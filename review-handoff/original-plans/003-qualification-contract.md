## Public switch evidence

Proposed additive property on the `Renewal` union's `Switched` member: `handoff`. Keep it optional in the public structural type for compatibility with callers constructing old event values; the new implementation always populates it on a planned switch. Historical aggregate `tail` stays unchanged. Consumers can use `Extract<Orchestration.Renewal, { readonly _tag: "Switched" }>["handoff"]`; a new package export is unnecessary.

`handoff` contains:

- `replacementSessionId`: source selected for activation. Existing `Switched.sessionId` is the retiring source because the event spreads `retired(current)` (`renewal.ts:1111–1123`, `source-slot.ts:352–354`); do not reinterpret it.
- `decision`: `"no-observed-start" | "count-complete" | "grace-elapsed"`.
- `finalClip`: a tagged union. `NoObservedStart` has no invented clip/count values. `Observed` has the last locally observed started `clipId`, `expectedVideoFrames`, `receivedVideoFrames`, and `videoStatus: "count-complete" | "incomplete"`.
- `grace`: `NotObserved`, or `Observed` with `origin: "Ended" | "Idle"`, `elapsedMs`, and configured `limitMs`. Values describe observations at eligibility, not time spent subsequently closing the source.

All counts are nonnegative safe integers and durations finite/nonnegative. `grace-elapsed` requires incomplete observed final video and elapsed time at least the configured grace. Count completion may occur before any Ended/idle timestamp; represent that with `NotObserved`. `NoObservedStart` means this process did not observe a start, not proof that the provider never played anything.

Extend the existing `FinalClip` facts in `renewal-state.ts`, and have the same pure decision used by `canHandoff` also return eligibility evidence. Do not reimplement the predicate separately in the harness. Preserve every existing true/false decision. The current decision is `finalClipSettled` plus sequence/idle/replacement guards; grace is 250 ms by default with a 100 ms spaced poll (`renewal-state.ts:122`, `renewal.ts:89–102`, `:1140`). Capture one immutable fact snapshot after `observedIdle()` and before `retired(current)` awaits pressure (`renewal.ts:1099–1111`).

Track the last observed clip identity and grace origin alongside the existing counters/timestamp in `source-slot.ts:247–260`. Reset on the same Started boundaries as today. A late Ended currently updates the timestamp; the evidence-only change must preserve that behavior and record the origin actually used, rather than quietly changing grace policy. Final counts are local received-frame accounting, not exact source attribution of every decoded frame, displayed frames, or audio completeness.

## Proposed nominal scenario and bounds

Use two independent grants, each with `maxSessions = 1`, a server-granted cap no greater than **50 s**, and **110 s** token duration. Those are existing repository caps (`gates.ts:27–34`), not current provider-price claims. Reserve both worst-case billed minutes using the freshly fetched rate before minting either grant. Keep the per-check ceiling **$1.50** and total ledger ceiling **$3.75**. Refuse if the current rate, grants, requested limit or existing ledger cannot fit; do not increase a ceiling automatically.

Use the granted lifetime from `openH3`, not an invented shorter lifetime. Require both nominal grants to permit the expected 50 s cap for this scenario; otherwise refuse before allocation because a different lifetime changes the timing design. Configure `lead: "40 seconds"`, `handoffGrace: "250 millis"`, and explicit `maxSessions: 2` on either constructor. For the proposed continuous constructor, also set `retainedSuccessfulCleanups: 1` and `maxUnresolvedCleanups: 2`, recording both. These values exercise successful-record compaction during final close while retaining room for both owned sources to fail cleanup; they do not qualify long-run boundedness, which belongs to 004's accelerated tests. If 004 changes the reviewed API, update this contract before the live checklist. A separate harness grant dispenser permits at most two open attempts and fails before allocation if a third attempt occurs. This guard includes failed attempts; it is stronger than `maxSessions`, which presently counts successful openings (`renewal.ts:486–538`). Never reuse an indeterminate grant to retry an allocation.

Nominal sequence:

1. Install evidence/cleanup tracking before opening the first source. Consume the handle's logical video and audio continuously after creation; these streams are single-reader and bounded (`media-buffer.ts:65–114`).
2. Subscribe to the gap-free handle observation and scheduler as-run before submitting keyed line `qualification-A`, requested length 5 s. Require its Started and Ended observations; no provider API changes playback.
3. Await Prepared and an Engine observation naming the second source as preferred. Submit keyed line `qualification-B`, requested length 5 s. Do not specify source affinity to override scheduler routing. Assert its observed Building/Ready source is the prepared source.
4. Once B is admitted for building on the prepared source, start `scheduler.drain({ finish: "accepted" })`. This exercises drain with an already acquired replacement. `stopRenewal` cancels only an Opening replacement and preserves a Ready one (`renewal.ts:926–938`), so do not start drain before the Prepared barrier.
5. Require exactly one planned Switched, A then B in retained Started evidence, both Ended, a completed accepted drain, and no third open attempt. Consume logical output through B's end, then close ownership and record canonical cleanup for both sources.

Use lineup with floor zero and a 5 s target so the check does not intentionally demand sustained filler. Record any actual filler behavior, but do not claim this two-line run qualifies every filler-policy case; those remain deterministic tests. There is no live forced lost-reply scenario: unknown-command and failure paths run against the twin and cause a paid run to fail and clean up, not silently recover until it happens to pass.

Time budgets, proposed and testable:

- Before the first allocation: 20 s monotonic setup limit. No automatic retry.
- Scenario work: stop admitting/waiting for nominal milestones at **40 s after first allocation**, independent of when the second source opens. Every wait uses the remaining shared budget, not a fresh 40 s timeout.
- Begin cleanup immediately after success/failure/deadline. Allow at most **20 s of harness-controlled cleanup observation** and retain any report already obtained. The server's 50 s caps remain the spending backstop, not a claimed client shutdown deadline.
- The CLI currently runs `bun qualify.ts` directly and has no parent supervisor. Do not invent automatic process termination or claim this plan bounds an uninterruptible SDK finalizer. Persist an incomplete checkpoint before entering cleanup, and update it if cleanup reports arrive. The existing rehearsal test's 150 s outer timeout is an external emergency bound; the paid checklist must separately name the maintainer/CI emergency deadline and intervention owner. If external termination becomes necessary, the last durable evidence stays failed/incomplete, the reservation remains, and remote caps remain the spending backstop. A stalled-close rehearsal must prove the checkpoint survives and never reports confirmed termination. Adding a production process supervisor is outside this plan.

The 40 s work budget is intentionally a qualification bound, not a guarantee hosted startup/build fits. Rehearsal must fit it with the proposed settings; a slow real run fails once and records why. Do not extend time, allocate a third source, or repeat the run to manufacture a pass. Before live authorization, calculate both cap-expiry wall instants from the allocation records, distinguish these from monotonic elapsed measurements, and include the exact commands and total reserved spend for all approved checks.

## Monotonic measurement and media attribution

Existing `collect.since(origin)` uses `Date.now()`, and `readInto` uses `Clock.currentTimeMillis` (`collect.ts:21–22`, `:94–105`, `:287–295`). Do not subtract those values to assert the new elapsed-time contract.

Add a narrow injected elapsed-clock adapter in `collect.ts`, captured from Effect's `Clock` service, using `Number((clock.monotonicTimeNanosUnsafe() - originNanos) / 1_000_000n)`. Use that same origin for every field inside the new `schedulerRenewal` evidence block and its media arrivals. Reuse the existing VideoReader/AudioReader and extend `readInto` with an explicit elapsed effect rather than writing duplicate frame-summary code. Preserve old default reader behavior for historical checks. Keep top-level `startedAt`/`finishedAt`, grant expiry, and existing legacy fields on their established wall-clock basis. Clearly document the new subtree's clock; do not compare its offsets with legacy span offsets or `AsRunEvent.at`.

Logical frames carry no source ID (`session/media.ts:20–45`). Reading `handle.mediaState` when a frame is dequeued is not proof of its source, because old frames can remain buffered. Proposed harness-only attribution: decorate each returned `Source.media` video/audio stream with a synchronous `Stream.tap` that records `(source.id, media.generation)` in a WeakMap keyed by the unchanged frame object. Pass the same objects onward. The logical-output reader looks up the tag; an untagged frame fails the criterion rather than being guessed. Current renewal forwards the same objects (`renewal.ts:460–475`, `media-buffer.ts:84`); test this seam explicitly and fail if that assumption changes. The WeakMap retains no additional strong references or media bytes.

Use the existing recorder's generation-reset behavior (`session/recorder.ts:14–35`) and source/generation tags to keep reader accounting honest across boundaries. Reuse frame summaries and arrivals; persist only IDs, counts, timings, digests and pressure. Record the last logical frame tagged to A's source and first logical frame tagged to B's source; their monotonic difference is the decoded logical-output gap. Require both and source order. Persist the observation without claiming exact encoded/presented continuity. Audio stays `unverified` for completeness even when block arrivals are recorded.

## Evidence schema and old-ledger compatibility

Keep top-level format `reactor-hosted-qualification/v1` and all existing check discriminators. Add optional `schedulerRenewal` with its own `version: 1`, `clock: "effect-monotonic"`, and `scenario: "two-source-accepted-drain"`. A partial run must remain encodable before allocation and at every milestone; schema-required complete success fields belong in final validation, not initial-file construction.

Proposed subtree fields:

- `configuration`: `constructor: "legacy" | "continuous"`, the actual work/setup/cleanup limits, lead, grace, clip lengths, `maxSessions: 2`, two-attempt cap and, for continuous, both retention options.
- `allocations`: zero to two records with slot ordinal, grant limits/expiry, session ID and wall allocation instant when known, monotonic allocation/close times, and canonical `SourceCleanup` codec when known. No grant JWT or owner record.
- `items`: A/B keys, requested duration, observed clip/source IDs when known, normalized tagged statuses and monotonic observation times; preserve Unknown/failure dispositions without provider text.
- `switches`: recorded observation time, retiring and replacement IDs, aggregate tail encoded with decimal counters, and the new handoff evidence captured by the SDK.
- `media`: logical video/audio summaries, bounded per-source/generation arrival summaries, attribution completeness and the decoded boundary above.
- `drain`: requested/completed times, accepted key set, outcome, and allocation count when requested/completed.
- `cleanup`: a discriminated legacy/continuous result when available, with explicit incomplete-record reasons. Legacy wraps the existing `Orchestration.CleanupReport`; continuous wraps 004's proposed `Orchestration.CleanupSummary` codec, which has no top-level `sessions` field. Preserve this distinction in schema and report rendering; do not coerce a compacted summary to a complete legacy report.

Add `required`/cross-field validation for this check rather than falling through the vertical default (`evidence.ts:384`). Require exactly two distinct allocated source IDs, both item outcomes Ended, ordered Started evidence, one matching planned switch, nonempty logical media on both sources, drain success with no later allocation, and confirmed canonical owned-lease cleanup for every allocated source. The two bounded allocation records retain their canonical source-close reports even when the continuous summary compacts one success. Validate those reports against the actual allocated session identities, then reconcile retained/omitted summary totals and dispositions; omission counters alone cannot prove those two leases terminated. With the proposed nominal settings expect two total retirements, one retained complete owned termination, one omitted complete owned termination, no incomplete rows and no exhaustion. Require named criteria to be present, not only that whichever criteria happen to exist pass. A missing second termination, duplicated source identity, impossible ordering or incomplete attribution cannot be a pass. The final combined hosted-qualified criterion additionally requires the continuous constructor.

Generalize the check-specific session-count/ceiling mapping in `gates.ts:42–44`, `:109–114`, `qualify.ts:1484–1489`, `:1606`, `evidence.ts:543–551`, conclude's termination checks, report rendering and cleanup text. A partially admitted new two-session run with a grant but missing worst-case reservation must conservatively reserve $1.50, not fall back to $0.75. Keep the single ledger lock and persist reservation before either token. Existing old `scheduler` ledgers continue decoding and reserve exactly as before.

Fault rehearsals cover first/second acquisition refusal, allocation then connect failure, second-grant overgrant, delayed/stalled termination, interruption after allocation, source-attributed lost enqueue reply through the real renewal path, missing Switched, missing video on either side, missing cleanup, and request for a third source. Canonical renewal already schedules replacement for an unknown enqueue (`renewal.ts:750–787`); the harness must exercise that real path and the final 002 semantics, not implement another recovery loop. Generic-engine behavior belongs to 002's separate fixture matrix.
