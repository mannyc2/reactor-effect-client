# Decision 002: Preserve existing source recovery; bound unresolved scheduler recovery

Source baseline: `c47e50c784f6889b542cf8ee316067b688ca4737`, 2026-09-26. This is a proposed implementation contract supported by source inspection, not a claim that new regressions were executed. It supersedes the premise that canonical renewal necessarily leaves an unknown enqueue on its original source until ordinary expiry.

## Evidence

The report in [#37](https://github.com/mannyc2/reactor-effect-client/issues/37) demonstrates a scheduler stall on a scripted Engine: L0 returns unknown, L1 is never dispatched, and L1 eventually misses its firm deadline. The scheduler policy does count unknown items and filler against its default cap of one (`scheduler-policy.ts:255–266`, `scheduler.ts:525`). The extrapolation to canonical renewal needs a different oracle, because its result hook already initiates replacement.

The complete existing path is:

1. `Submission.make` forks one committed execution and retains its outcome; joining or abandoning the wait cannot replay it (`Submission.ts:50–86`).
2. A Session reply timeout leaves a submitted correlation slot reserved until late reply or generation retirement (`session.ts:814–821`). H3 waits for metadata acceptance, with a default 15-second command budget and an additional 5-second reconciliation window (`h3/_internal/client.ts:129–139`, `:724–758`). These limits do not prove rejection.
3. H3 runs the committed result hook before returning the outcome; its hook has a separate default one-second deadline (`h3/_internal/client.ts:803–835`). The source projects the same result into the orchestration hook (`orchestration/h3-source.ts:451–466`).
4. Renewal records the result, completes accounting, and on **every unknown result** calls `scheduleRecovery(target, result.failure, "replace")` (`renewal.ts:750–787`). `SourceSlot.recordResult` also sets its sticky indeterminate flag (`source-slot.ts:223–228`).
5. `scheduleRecovery` fences the slot into Recovering before forking recovery under the command permit (`renewal.ts:449–457`). Repeated recovery can escalate to replace without reopening it (`renewal-state.ts:16–41`). Recovery joins the existing committed submission and chooses replacement because indeterminate or replace-mode requires it (`renewal.ts:363–372`, `renewal-state.ts:122–127`). It does not enqueue the original key again.
6. `replace` collects loss evidence, closes the source, selects an already acquired replacement or acquires a new one, and restores autoplay (`renewal.ts:311–360`). With renewal stopped and no replacement, it explicitly fails rather than allocating (`:335–338`).

`Renewal.test.ts:351–382` already expects an unknown commit to produce a second source and a Replaced event, no reconnect, and exactly one dispatch of the uncertain submission. `SchedulerFates.test.ts:468–508` wraps a real Renewal engine and expects a replacement within six seconds of its scripted unknown; it does not test a later line's progress. `SchedulerRenewal.test.ts:436–472`, in contrast, overrides engine enqueue methods above the real result hook; its synthetic unknown bypasses this automatic replacement. Keep those two fixture meanings distinct.

There are two actual remaining gaps to address:

- A generic Engine can remain Ready forever after unknown; the scheduler has no finite failure policy. Absent snapshots cannot prove capacity is free. `Engine.observe` is a local state/subscription pair (`types.ts:154–163`; `observation.ts:120–122`), not a remote dispatch barrier.
- The asynchronous recovery fiber has no all-cause supervision at its fork (`renewal.ts:457`). `replace` catches typed failures with `Effect.catch(fail)` (`:360`), but a defect from a custom source or cleanup can terminate the fork without completing `engine.failure`. A source already marked Recovering is then excluded from normal renewal progress (`:1023–1029`). Add a controlled defect regression before changing this path.

Local retirement is not confirmed remote termination. Closing counts as closed (`renewal-state.ts:46–47`), so Engine state excludes a slot once closure starts (`renewal.ts:823–825`), before `SourceSlot.close` has returned (`source-slot.ts:123–136`). The existing terminal Unknown means this scheduler can no longer reconcile the source; it does not establish that the remote rejected or never played the clip. Session cleanup separately records remote confirmation (`session.ts:1369–1394`, `session/_internal/cleanup.ts`). An HTTP deletion response alone is not proof (`coordinator/_internal/client.ts:651–658`). Preserve that distinction in docs and assertions.

## Decision

Keep the strict source-local build reservation, no-replay key behavior, and existing source-owned replacement. **Do not add a second Engine recovery/retirement API and do not implement timed capacity release.**

After plan 001, add `SchedulerOptions.unknownRecoveryTimeout?: Duration.Input`, default **60 seconds**, positive and finite, maximum **10 minutes**. This is a deadline for continued scheduler service while a preferred-source unknown remains or unknown fate holds a drain, not a remote rejection or capacity-release deadline. At expiry, settle the scheduler through plan 001's terminal boundary with the existing `Timeout` ReactorError reason, an SDK-authored message and `context.operation: "scheduler.unknownRecovery"`, retaining the original uncertain command cause(s) in diagnostic detail. Do not add another error class or reason. Unknown items terminate as Unknown; known started/ended evidence remains unchanged; other unsettled accepted work receives the existing Scheduler failure disposition. Pending drain/withdraw/control calls fail, and subsequent admission is closed. The owner still owns orchestration cleanup.

Characterize the unsupervised recovery-defect path, but keep direct Engine all-cause supervision as a separately scoped follow-up. Do not turn a defect or interruption into a generic ReactorFailure with diagnostic detail: preserve original Causes according to CONTRIBUTING and plan 001. A coherent direct Engine change would also need to specify failure Deferred, typed event/media channels and media-buffer behavior; the scheduler watchdog does not require that redesign. Its elapsed timeout is a genuine separate service-policy failure, not a relabeling or handling of the original recovery defect. If the scheduler itself defects, plan 001's original-Cause terminal path still applies.

No additional source allocation is introduced by this option. Canonical renewal already owns the replacement policy and its cost. Success means canonical recovery lets a distinct later line dispatch on a usable replacement; a nonrecovering generic Engine instead gets an explicit service failure. Do not describe the latter as recovered continuity or same-source liveness.

## Bounds

The 60-second default is a proposed service policy, chosen to allow the existing 30-second source acquisition budget (`renewal.ts:498–506`) and ordinary ten-second recovery/accounting work (`:79–84`, `source-slot.ts:98–120`) before failing service. It is **not** their proven total maximum. H3's command/reconciliation budgets run before the scheduler sees unknown; the new deadline starts at scheduler observation of the unknown outcome. Applications with intentionally longer recovery or HTTP limits can select a larger finite value up to ten minutes.

Every unknown item/filler outcome records its first monotonic observation time. An active episode's deadline is the earliest such time plus unknownRecoveryTimeout among the unknown reservations restricting the preferred source, or among unknown fates blocking an active drain. **Arm immediately when a preferred-source unknown consumes even one capacity reservation, including when maxBuildsInFlight is greater than one, spare capacity remains, and no later item is waiting.** Do not wait for actual demand or a full cap. An unfenced unknown restricts the preferred source as it does in the current capacity calculation. This explicit definition avoids a demand-dependent timeout.

The episode continues across local retirement while no live Ready preferred replacement can resume service. An old unknown on source A does not prolong a capacity episode when Ready preferred B can accept work; retain A's fate and original observation time separately. Repeated unknowns, duplicate submit, snapshots, overflow/reobserve, ordinary events and wall-clock corrections never extend an active deadline. A new independent unknown after capacity recovery receives its own observation-based deadline. If a later drain is now blocked by older retained uncertainty, use that uncertainty's **original** deadline; fail immediately if it has already elapsed. Starting drain is not permission to extend an unresolved dispatch's age.

An ordinary capacity episode ends when keyed evidence removes its unknown blocker or a live Ready preferred replacement can accept work; the old uncertain key need not have a known playback outcome. A drain episode ends only with truthful completion or failure. Local disappearance of the old source alone cannot erase the watchdog while replacement is still unavailable: closure can start before cleanup or acquisition finishes. Keep only the episode's original deadline after individual item/filler records become terminal while replacement is unavailable; do not introduce another provider-fate registry. Ready B and locally retired A end A's capacity watchdog without asserting A's remote cleanup was confirmed. Resolve equal-time races from already accepted actor evidence: a recovery completion processed before timeout wins; an already published timeout cannot be undone by late evidence.

The watchdog must run independently of the actor and engine command permit, using plan 001's idempotent terminal-settlement boundary. Recheck only the retained episode identity/deadline at expiry; do not await engine.state, stopRenewal, or cleanup to decide whether its own deadline elapsed. Merely enqueueing a Tick or failure message is insufficient: the actor currently waits for `engine.stopRenewal` during Drain (`scheduler.ts:1713–1719`), which can wait behind a stalled recovery holding the permit. Do not make expiry wait for that effect. Fence command admission at the terminal boundary and test that no queued fresh enqueue dispatches after failure.

This promises bounded **failure notification and waiter settlement**, subject to a running JS runtime. It does not promise bounded cleanup completion for arbitrary custom Sources. `SourceSlot.close`, H3 close and Session close are uninterruptible; custom close/finalizer code can stall. Effect rc.117 implements `timeoutOrElse` via `timeoutOption` and `raceFirst` (`effect/src/internal/effect.ts:3806–3884`), and documents cooperative interruption (`effect/src/Fiber.ts:353–377`): wrapping that cleanup with a timeout does not prove cleanup ended. Do not abandon its resource ownership or synthesize a confirmed CloseReport. Scope/handle close continues to join owned cleanup; retain and report any actual incomplete cleanup evidence.

## Generic engines

No new optional Engine method is needed. Engines that return unknown can provide keyed evidence or retire their fenced source under their own policy. Engines without a source fence retain the original uncertainty until evidence or scheduler failure. They receive the same default 60-second deadline from the original unknown observation whenever a preferred-source reservation is uncertain, even with spare capacity/no demand, or its fate holds a drain. None may clear a reservation merely because its state is Ready or a later snapshot omits the key.

Keep unknown filler identities in an index/source ledger instead of the current scalar before supporting overlapping uncertain sources. Multiple sources can be uncertain even with the current strict cap: a preferred replacement can receive a distinct filler while the retiring source still has unknown filler. Never overwrite an unresolved entry. Advance the index once when abandoning that dispatch identity for a replacement; same-index retry remains allowed only for the already-supported definitely-not-submitted outcome. Retire/adopt each ledger record independently. Count only entries belonging to the preferred source for capacity, but retain all entries for drain and the recovery deadline.

Bound the uncertain filler ledger at 4,096 records, matching the existing committed-submission bound in `source-slot.ts:214–218`. This is a proposed local memory bound, not provider capacity. On exhaustion, fail scheduler service with the existing Overflow reason before dispatching another filler; retain every already uncertain identity until terminal settlement. Do not evict an unresolved key or add a public tuning knob for this exceptional custom-engine case. Canonical maxSessions and source retirement ordinarily keep the ledger far below it.

## Drain

Keep the first-selected drain mode and immediate `stopRenewal` allocation fence. A real unknown result already initiates source recovery; after stopRenewal it may use an acquired replacement, or fail if none can continue. Do not reopen renewal to make a drain succeed.

During accepted drain, allow other accepted work and its required filler to progress on a usable source. Unknown alone does not justify indefinite filler. Uncertain fate still holds successful completion; the watchdog supplies a bounded failure instead of silently ending a drain. A watchdog firing while `stopRenewal` waits must settle drain and item waiters without claiming that the blocked cleanup finished. Later cleanup results remain owned and inspectable.

## Compatibility

This adds an option but also changes default behavior: a custom Engine that previously let uncertainty block admission or drain for its source lifetime now fails scheduler service at the original unknown observation plus 60 seconds while a preferred-source reservation remains uncertain or its fate holds drain. Uncertainty on an older source that does not block current service still retains its truthful fate. Canonical recovery already replaces unknown sources; this proposal does not introduce that paid behavior. Preserve maxBuildsInFlight semantics and all public as-run tags.

Document the new default and migration in the package README and changelog. Treat it as a behavior change requiring the repository's applicable release policy, not automatically as an invisible patch. Consumers depending on long uncertainty waits must select a larger finite budget or deliberately revise their application contract; no infinite opt-out is proposed. The original issue's script should now demonstrate bounded failure, while the canonical fixture must demonstrate L1 continuity on replacement. Both are required before claiming #37 resolved under this contract.

## Regression matrix

1. **Actual canonical path:** real Renewal plus SourceFixture, long source lifetime, L0 unknown through the source's committed result hook, L1 submitted two seconds later. Assert one L0 dispatch, old source closure, one replacement, no reconnect, L1 dispatched/started on the replacement before a fixture deadline of 50 seconds, and truthful L0 terminal Unknown. Use gates to determine milestones, not a six-second sleep as evidence. Repeat with filler unknown and real H3/Session fixture coverage of hook forwarding.
2. **Generic script:** inject unknown at Engine.enqueue, keep the source Ready and empty. At 59,999 ms after unknown the failure is pending; at 60,000 ms plus scheduled effect turns it has settled. L0 is terminal Unknown, accepted L1 is Scheduler-failed rather than silently dropped by an unrelated later deadline, and neither key was replayed. Test explicit ten-minute maximum, invalid zero/negative/infinite/accessor options, and a short configured duration.
3. **No deadline extension:** same-key submit, empty snapshots acquired before and after dispatch, overflow/reobserve, repeated ticks, a second unknown, and forward/backward wall-clock jumps. The first blocking episode deadline remains fixed. Cover maxBuildsInFlight greater than one and no queued demand: the original observation still anchors the deadline immediately. A later independent unknown after recovery has its own deadline. Ready B accepting work clears a capacity episode even while old A has uncertain fate; a subsequent drain blocked by A uses A's retained original deadline and fails immediately if overdue.
4. **Late proof:** keyed Building/Ready/Started before deadline adopts without replay and restores normal capacity accounting. Proof after terminal failure cannot revive the scheduler. Filler records for A and B reconcile independently; only preferred-source reservations block its builds, and both records hold successful drain until resolved. Ledger exhaustion fails before an additional filler dispatch and retains the existing identities.
5. **Retirement is not cleanup proof:** hold source.close after its phase becomes Closing; verify source absence does not cancel the recovery episode while no Ready replacement exists. Deadline notifies failure despite blocked close; releasing the gate later produces the original cleanup report. Do not assert remote confirmation from source disappearance.
6. **Recovery defect characterization:** inject a defect in source state/close/reconnect or replacement setup; record whether the existing recovery fork terminates without publishing engine.failure, and verify the independent scheduler deadline still reaches truthful settlement. Preserve the original defect Cause in its actual owner; do not wrap it to force a typed Engine result. Track direct Engine/media all-cause supervision separately. Expected close interruption does not fabricate a second scheduler failure. Repeated unknown/recovery requests cannot create duplicate replacement acquisition or reopen a terminal source.
7. **Drain races:** both modes, unknown before/during stopRenewal, already acquired replacement versus none, and stopRenewal blocked behind recovery. Assert no post-fence acquisition, settled waiters on timeout, no false Dropped/Started, and preserved first decisive evidence.
8. **Regression preservation:** known-not-submitted paced retry, old-source unknown with usable replacement, active/queued known-clip loss during forced replacement, original source fences, history idempotency, ordinary successful drain, and plan 001's immediate scope closure on failure.

Run the focused suites on Node and Bun, then the existing portable, package and required build/typecheck/lint gates from plan 002. No tests, install, build or paid session were performed while writing this decision. The decision is implementable without provider-ordering research; offline regressions must verify the inferred behavior before issue closure. A finite deadline can fail a legitimate but slow recovery. That is the explicit proposed service-policy tradeoff; it never turns uncertainty into rejection or admits another uncertain request on the same full source.
