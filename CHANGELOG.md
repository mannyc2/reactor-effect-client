# Changelog

All notable changes to `reactor-effect-client`, `reactor-effect-browser` and `reactor-effect-native` are documented in this file. The three packages are always released together, with one version.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `Playout.ClipModel` and the `model` option of `Playout.make` and `LocalSource.open`, so a playout plans for a model other than H3 and a local renderer can air clips shorter than 5 s. H3 remains the default.
- `Source.model`; the playout refuses a source whose model name differs from its own before sending commands.
- `H3Source.model`, the H3 clip model and its documented request limits.
- `Playout.Service<Req>` for application services that plan another model's requests.
- `FastH3`, a provider for Reactor's FastH3 (`reactor/fast-h3`) over a connected `Session`. Requests take a frame or clip id as opener and closer, with lengths of 5.167–14.375 s aligned up to the frame grid. `ReactorTest` simulates its queues and playback. One paid raw-session probe confirmed the deployment contract and observed length alignment; no paid run has qualified this provider or a FastH3 playout. Hosted FastH3 refused H3's undeclared `reference_images` field.
- `FastH3Source.open`, `resume` and `model`, so `Playout.make` can air FastH3 across session caps. Automatic continuations use only built, retained clips. A missing playout hint is omitted and reported before the single submission; an explicit request opener takes precedence. Post-send failures and dispatch outcomes pass through unchanged, with no failure-triggered refresh or resend. H3Source uses the shared source engine with its public API and behavior preserved; hosted FastH3 provider/playout qualification is pending.
- `ClipModel.builtSeconds`, the length a model builds for a requested length: H3 and FastH3 align it up to their frame grid, and a renderer that builds what it is asked answers the length itself.
- `State.estimates.lanes` and `State.estimates.filler`: each lane's builds and filler's apart, per requested second, beside the estimates over every build, which keep their meaning. `Playout.BuildSpread` names a median and p95 of builds.
- `Ledger`, the paid sessions an application owns, each recorded before it connects and ended until Reactor confirms it. The SDK owns that protocol and the application the storage: a `Ledger.Store` it provides through `Ledger.layer`, or a JSON file through `Ledger.layerFile`, or memory through `Ledger.layerMemory`. `ledger.source(opener)` is a playout's `open`. Before it allocates, it resumes the recorded session that ends last, while a minute of its cap remains, and ends the other sessions recorded for its coordinator, waiting until Reactor confirms each end. Then it records a fresh session before the session connects. A closed source, and any failure after the record, ends the session and forgets it once Reactor confirms the end; until then the entry is marked `ending` and the end is asked again. `ledger.release` ends every recorded session the ledger does not hold. One store belongs to one process and one Reactor account.
- `H3Source.opener` and `FastH3Source.opener`, which open and resume each source's sessions for a `Ledger`: `ledger.source(H3Source.opener({ tokens }))`.
- `CoordinatorClient.terminateUntilConfirmed` and `ConfirmedTermination`: ends a session and asks again, 5 s after the first end and doubling to at most 5 minutes apart, until Reactor confirms it. It fails at once on a `DELETE` refused with 401 or 403, and when a schedule the caller passes ends first.
- `References`, which loads reference images and voice samples from where an application keeps them: a base64 `data:` URI, a file or an http(s) URL. `References.image` and `References.audio` read at most `maxBytes`, 16 MiB by default (a session's upload limit, where H3's validation admits 25 MiB), within a `timeout` of 10 seconds by default, then validate the bytes as H3 does. `References.locate` turns a URI or an absolute path into a location without reading it, `References.file` and `References.url` make one, and `References.read` reads its bytes alone. Each location asks only for the service it needs: a file a `FileSystem`, a URL an `HttpClient`. No error or span names the location.

### Changed

- `ReactorTest` keeps a dropped session `INACTIVE` until it is terminated, reconnects or reaches its cap, matching hosted behaviour. It previously ended the session after 30 seconds. Tests that need Reactor's documented disconnect deadline can use `DisconnectEnds { after }`.
- A clip not built yet is planned at the length its model builds, so `place`, firm admission and cap checks no longer err by up to a grid step for a length not asked for before. On the simulated Reactor, a clip placed behind a 7.3 s request, which H3 builds as 8 s, started 473 ms after its `startsAt` before, and 17 ms after.
- `LocalSource` builds the length its model builds when its hook states none: a stand-in for H3 now builds H3's lengths.
- Builds are projected per built second, each lane at its own rate once three are measured, and filler at filler's. One median over every build, filler's included, projected every item: a local renderer whose filler builds at once, and whose items took 0.8 s a requested second, admitted a firm item as if its 4 s build took nothing. It is now refused with `WouldMissDeadline`.
- `CoordinatorClient.terminate`, and so `session.close`, confirms a session gone only when two reads in a row find it gone; one missing read used to confirm it. A coordinator can answer 404 for one read of a running session, so after a `DELETE` that did not take, such a session was reported confirmed ended and `Session.mayStillBill` said false.

### Documentation

- The session and cost-control guidance no longer promises that Reactor ends a dropped session after 30 seconds. Reactor documents that deadline, but a hosted session whose owner was killed stayed live past 60 seconds and was billed until the API key ended it. End sessions explicitly and cap them.
- The cost-control guide records and ends sessions with the `Ledger`, in place of its hand-written owner records and start-up pass, and the livestream example opens its sessions through the ledger, kept in `ledger-<mode>.json` in place of `allocations.jsonl`.
- The H3 guide loads references with `References`, and the terminal, avatar and native capture examples read theirs through it; the capture example refuses a bad image before it mints a token.

## [0.10.0] - 2026-10-02

0.10.0 moves the SDK to Effect 4.0.0 and adds `ViduS2Avatar`, a provider for Reactor's Vidu S2-Avatar, a character made from one photo who talks with a caller in a live call. Every package now peers on Effect `~4.0.0`, so a project on Effect 4.0.0 or a later 4.0.x patch can add it; a project on `4.0.0-rc.117` moves to Effect 4.0.0 first, including its own `effect/unstable/*` imports. The native Rust sources are unchanged since 0.9.2.

Qualification: the main CI run that built these archives passed every job: the shared portable checks; the portable suites on Ubuntu with Node 22 and 24 and on macOS with Node 24; the native addon on linux-x64 and on darwin-arm64, with its suites on Node and on Bun and the Chrome browser/native WebRTC test on Node; and the pack/install smoke of all five archives, whose fresh install takes Effect through the `~4.0.0` peer. Two paid `character` runs drove `ViduS2Avatar` on hosted Reactor on this source with Effect 4.0.0, under Bun with the 0.9.2 linux-x64 addon: one passed every criterion, and one failed at its first command with a native `Protocol` failure whose cause is unknown. No paid H3 run has used Effect 4.0.0; H3 and the playout use the same session, connection and native paths the `character` run exercised.

### Added

- `ViduS2Avatar`, a provider for Reactor's Vidu S2-Avatar (`reactor/vidu-s2-avatar`): a character made from one photo, who talks with a caller in a live call. Over a connected `Session` it makes or attaches the avatar, lists voices, starts a call, steers it with `say`, `interrupt`, `updateCall` and reference images, and ends it, and it follows the model's state, transcripts and `command_error`s. It resumes the character's `main_video` and `main_audio` as each call goes live: on hosted Reactor a call's picture came only after that resume. `endCall` waits up to the provider's `callTimeout`, 60 seconds by default, because hosted Vidu answered `end_call` 6.9 to 13.2 seconds after it was sent. On Node and Bun the caller speaks only through `say`, since the native host sends no microphone audio. On hosted Reactor, the paid `character` check ran the provider twice on Effect 4.0.0: one run passed every criterion, from the avatar to the call's picture, an answer to `say` and `endCall`; in the other, the connection failed with the native addon's `Protocol` failure 21 ms after the provider's first command, for a cause not yet known.
- `Refused`, a `ReactorError` reason for a command a model refused with a code it documents. It carries the `code`, the model's `origin` and `retryable`, and keeps the model's sentence redacted.
- `DecodedMedia.setTrackActive` pauses or resumes a received track on a decoded connection, as `TrackMedia.setTrackActive` already did with a browser's tracks.
- `ReactorTest` simulates Vidu S2-Avatar beside H3, with `Timing` ranges for making an avatar, a call going live, an answer, its speech and the hang-up, set from the paid runs.
- An avatar example, `examples/avatar`: a call with a character from Node that runs offline on `ReactorTest` without a key.

### Changed

- **Breaking: Effect 4.0.0.** Every package's `effect` peer is now `~4.0.0`, as are `reactor-effect-native`'s `@effect/platform-node` and `@effect/platform-node-shared` peers, in place of an exact `4.0.0-rc.117`. A project already on Effect 4.0.0 could not add 0.9.2: npm refused the pair, and a forced install failed to load, because Effect moved every `effect/unstable/*` module to `effect/*` from rc.118 on. The peers admit Effect's 4.0.x patches and stop before 4.1: Effect 4.0.0 marks the modules the SDK builds on (`effect/http`, `effect/rpc`, `effect/process`, `effect/workers`) unstable, which may change in a minor release. Effect asks for one version across `effect` and every `@effect/*` package, so pin `@effect/platform-node-shared` to your `effect`'s version with an override wherever `@effect/platform-node` is installed, now with `reactor-effect-native` too.
- `ReactorError`'s reasons include `Refused`, so a `switch` that handles every reason needs a case for it.

## [0.9.2] - 2026-10-01

0.9.2 fixes planned clip lengths, firm admission and follower wakes near session caps, and adds the documentation site and offline examples. The five packages share version 0.9.2; public modules and exports are unchanged.

Qualification: portable Node and Bun suites, policy properties, native CI and installed-package checks. No paid hosted run exercised 0.9.2. Firm admission projects measured timings: slower builds, seams and later edits can still put an admitted item past its deadline.

### Added

- A documentation site, [mannyc2.github.io/reactor-effect-client](https://mannyc2.github.io/reactor-effect-client/), with concept pages, guides, the hosted evidence, `llms.txt` and `llms-full.txt` for coding agents, and a playground that runs H3 Studio on `ReactorTest` in the browser.
- An Agent Skill, `skills/reactor-effect`, installable with `npx skills add mannyc2/reactor-effect-client`.
- A prompt-to-end quickstart and a terminal video viewer, both running offline on `ReactorTest` without an API key and using the same application with hosted layers.

### Changed

- The package READMEs open with what each package is for and link the documentation, which now carries the contracts the client README spelled out; the npm descriptions, keywords, homepage and issue tracker say the same.

### Fixed

- Near a capped session's cap, the filler covering the wait for an `At` item could go late, or not at all. A clip tiling that wait was too long to air before the cap, so none was sent; as the wait shrank, a clip sized to it came to fit, but nothing woke the playout then, and it went only with the next event, if one came before the cap. The playout now asks at once for the longest clip that airs before the cap, if `lengths.min` does.
- A follower's fence or build cover could change between the plan's wakes. The plan now wakes as the clip on air falls to the readiness margin and counts a follower's cover deadline back from that clip's end, so every look names the same instant. Filler also waits behind a held follower when an earlier build stops fitting before the session's cap.
- A `Playout` item whose request names no `seconds` is sent asking for 5 seconds, the length the plan counts it at, and a filler clip whose request names none asks for the `seconds` the playout asked the `clip` callback for. In 0.9.0 both went to H3 without a length, so H3 built them at its session's clip length, 15 seconds by default: a clip planned at 5 s aired 15.08 s, and everything behind it aired later than projected. An item's key now names the same item whether its request leaves out `seconds` or asks for 5.
- A firm item is refused with `WouldMissDeadline` when it cannot start before its `startBy`. In 0.9.0 admission counted an item ahead that was not built yet by its build time alone, never its air time, so a burst of firm items was accepted and the later ones were dropped as `late`, some while items submitted after them aired. Admission now counts every clip queued ahead at its own length, built or not, and runs the plan forward, as `place` does, so a boundary the next clip is not Ready for goes to filler, as it does on air. A firm item already admitted is dropped as `late` as soon as the clips ahead put its earliest start past its `startBy`. On the simulated Reactor at the hosted median seam, over 288 bursts and paced arrivals of firm items, 703 of 2,269 admitted items were dropped as `late` before, and none of 1,601 after.
- `Start.Manual`'s documentation said a held item is built ahead. It is built ahead only while filler keeps the runway at its floor, and otherwise once released, as always on a playout without filler.

## [0.9.1] - 2026-10-01

0.9.1 fixes `follows` and `place` from 0.9.0, and makes queued work traceable to its caller. Most importantly, a `follows` item could leave the air dark until its session's cap, with the as-run reporting a clip `Started` that never aired. H3 clip operations now fail, instead of waiting for ever, once Reactor ends their session, and `ReactorTest` bills at H3's current rate. The public API is unchanged: no export is added, renamed or removed. The native Rust sources are unchanged.

Qualification: the main CI run that built these archives passed every job: the shared portable checks; the portable suites on Ubuntu with Node 22 and 24 and on macOS with Node 24; the native addon on linux-x64 and on darwin-arm64, with its suites on Node and on Bun and the Chrome browser/native WebRTC test on Node; and the pack/install smoke of all five archives. No paid hosted run has exercised 0.9.1: the playout fixes were found and checked on `ReactorTest`, Reactor simulated in memory, by an adversarial review and seeded sweeps, not on hosted H3. What hosted H3 does when autoplay is turned off with a clip armed is unrecorded; the fix and its backstop do not depend on it. Two known gaps remain for 0.9.2: deep property runs (20,000 scripts) show that, near a session's cap, a build or filler clip can fall due between the plan's wakes and go out late, and firm items can still be admitted that admission should refuse. A provider `Started` event is not proof of encoded output.

### Fixed

- A `follows` item could leave the air dark until its session's cap. Its fence turned autoplay off on the session on air at moments it did not check, such as when the follower was picked to build just as a clip ended. If that command reached H3 while the next clip waited out its seam, H3 named that clip playing and never started it: the as-run said `Started`, nothing aired, and nothing started the clip again until the session's cap ended it as `Lost`. On the session on air the fence now goes up only while a clip whose start the provider reported plays with more than a readiness margin left, since a state read inside a seam names the next clip playing before it starts. A clip held that way anyway is started with `play` once a state read shows nothing playing.
- A follower's start paid for commands it did not need: at its own boundary the fence turned autoplay off and on again, and every start the playout made itself sent `play` twice, the second refused, holding the session's commands for a round trip. A follower now starts as any boundary does, and each such start sends one `play`.
- A follower not Ready when its clip failed on air was not dropped, as it was when that clip ended: it aired after the dark gap, reported as following that clip. A follower of the clip on air when its session was lost was carried to the replacement, built again and aired seconds later, also reported right after that clip. Both are now dropped as `displaced`, as `follows` promises; one already Ready on the replacement still starts right after the loss, and a planned switch keeps a follower's place.
- A clip whose late or firm deadline passed while its start was under way, with autoplay fenced and a `play` of it in flight, was withdrawn as `late`, and its follower was dropped as `displaced` at once; then the start landed, and the clip aired without its follower. A clip is no longer withdrawn as late while a `play` of it is in flight, or after one that succeeded until its start shows, so such a deadline can be overrun by up to that round trip.
- With nothing submitted after the call, a clip submitted as `place` said could still be dropped as `displaced`: on `ReactorTest` with fixed build times, 13 of 400 renewal forecasts and 2 of 400 forecasts away from a renewal. `place` counted no command between the build slot freeing and the clip's enqueue, though the move another clip's Ready asks for, or the fence before a follower's build, goes first, and the follower was dropped as projected late meanwhile. It also took any build on a replacement to fit, though the playout sends none that cannot air before that replacement's cap. `place` now keeps a provider command's round trip, 0.2 s, beyond its readiness margin, checks a replacement's cap as the playout does, and a follower whose fence is going up is not dropped as projected late. Over the same 800 forecasts one is still displaced, where the replacement opens later than `place` projects, and `startsAt`'s errors are unchanged; a few answers move a clip later, and some to null: near the last boundary a clip can make, on sessions of any length, and where a replacement could not air the clip before its cap.
- A firm item could still be dropped `late` at a boundary it would have made, or refused with `WouldMissDeadline`. Through its seam, H3 names the next clip playing while it still lists that clip Ready, and the playout counted its length twice, as the rest of the clip on air and among the Ready clips, whenever a state read fell in the seam; the runway, filler, cover, exposure and cap checks read the same count. A session's Ready clips are now counted without the one it plays.
- A playout's queued work is traced under the caller that caused it. In 0.9.0 every item's commands ran in the playout's acquisition trace, whoever submitted the item, and the application's spans inside `LocalSource` hooks ran in the source's acquisition trace. Now each command the playout sends for an item is a `Playout.command` span under the span that first submitted the item, through waiting, retries, a duplicate submission and a renewal, with the source's spans, such as `H3.enqueue` and `Session.command`, beneath it; it ends with the command's outcome and carries `reactor.playout.item.key`. `LocalSource.build` and `LocalSource.present` are spans under the span that enqueued the clip. `Playout.open`, around each session the playout opens, and the `Playout.command` of an autonomous command, such as filler or autoplay, each start a trace of their own, linked to the acquisition's span.
- Work that an acquisition sets going and no caller causes keeps the acquisition's decision not to sample: `Playout.open`, an autonomous `Playout.command`, the hooks of a `LocalSource` clip enqueued outside any span, `H3Source.recover` and a session's own `Session.reconnect` are unsampled under an unsampled acquisition span. Under a sampled one, `MinimumTraceLevel` decides, as for any root. A session's own `Session.reconnect` was sampled by the trace level alone before. An item's work takes its submitter's decision.
- H3's read and control calls have spans of their own, `H3.getState`, `getQueue`, `refresh`, `pop`, `move`, `play`, `stop`, `setCanvas`, `setAutoplay`, `setFlushOnClipEnd` and `reset`, which fail when H3 refuses the call though its `Session.command` received the reply. `H3Source.recover` traces each recovery from a dropped connection, through the reconnect and the read back, as a root linked to `H3Source.open` or `H3Source.resume`. `CoordinatorClient.downloadClip` traces the playlist wait and the segment download, with the session id and no URL.
- A command or control request refused before it is sent records a failed `Session.command` or `Session.control` span with `reactor.command.outcome` `not-submitted`, and an invalid `Reactor.create` or `Reactor.attach` records its span; neither left a span before. `Session.command`, `Session.control`, `Session.upload` and `Session.close` carry `reactor.session.id` once the session's id is known.
- An H3 clip operation no longer waits for ever once its session has ended. When Reactor ends the session, at its cap or by content moderation, or the application closes the session while the provider is still open, `reached` and `ended` fail with why (`TerminalSession`, `Moderated` or `Closed`) and `facts` reads `indeterminate`. The provider fails for good with the same error, so `provider.failure` completes and its commands are refused, not submitted. Any other failure that ends the provider, such as an observation that overflowed, fails the operations too. In 0.9.0 they waited until the provider's own scope closed. A session with `reconnect: false` never reads that Reactor ended it, so there only a moderation verdict or the application's close ends the wait before the provider closes. A `Playout` over `H3Source` was not affected.
- `ReactorTest` publishes and bills H3 at 350 credits a second by default, the rate Reactor's pricing API stated on September 30, 2026. It was 125, so a simulated bill, and any cost an application worked out from the simulated `pricing`, was 2.8 times too low. `creditsPerSecond` still sets another rate.
- Doc comments that disagreed with the code. `H3.h3ReferenceTurboRealtime.prompt.maxChars` (12,000) is not enforced: H3 documents no character limit, only a budget of about 2,000 tokens that fails the clip at build, and a request's only local bound is 1 MiB of UTF-8. A `Reactor.Options` deadline must be positive and at most 10 minutes, and `heartbeatInterval` may also be `"Infinity"`; a negative infinite `heartbeatInterval`, which turned heartbeats off, is now refused too. `H3.Options` and a call's own `replyTimeout` or `uploadTimeout` take any finite, non-negative duration. `CoordinatorClient.Rate` adds that Reactor's dashboard lists sessions to the second.

## [0.9.0] - 2026-09-30

0.9.0 lets a caller ask where a clip would air before writing it, and hold the clip to that place: `Playout.place` projects the boundary a clip submitted after the caller's own work would make, and `follows` keeps an item right after the clip it was written to follow, or drops it as `displaced`. The coordinator's HTTP client is renamed `CoordinatorClient`, and the transport schemas move to `Peer`, so a host implements the transport without importing the HTTP client. It breaks the 0.8 API, so a `^0.8.0` range does not include it. The native Rust sources are unchanged.

Upgrading from 0.8.0:

| 0.8.0                                                                                                | 0.9.0                                                                                                                  |
| ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `reactor-effect-client/Coordinator` and the root `Coordinator` namespace                             | `reactor-effect-client/CoordinatorClient` and `CoordinatorClient`                                                      |
| `Coordinator.Coordinator` service and `reactor-effect-client/Coordinator` key                        | `CoordinatorClient.CoordinatorClient` and `reactor-effect-client/CoordinatorClient`                                    |
| `Coordinator.Track`                                                                                  | `Peer.Track`                                                                                                           |
| `Coordinator.Mapping`                                                                                | `Peer.Mapping`                                                                                                         |
| `Coordinator.IceServer`                                                                              | `Peer.IceServer`                                                                                                       |
| `Coordinator.IceCandidate`                                                                           | `Peer.IceCandidate`                                                                                                    |
| `Coordinator.mintToken`, `Coordinator.pricing`, `Coordinator.inspect`, `Coordinator.terminate` spans | `CoordinatorClient.mintToken`, `CoordinatorClient.pricing`, `CoordinatorClient.inspect`, `CoordinatorClient.terminate` |

- An exhaustive switch over `AsRunStatus` must handle `Dropped` with reason `displaced`.
- A hand-written `Playout` service needs `place`.
- An insert after an `At` item no longer takes that item's `late`: past the anchor's time it airs at the next boundary, where before it was dropped with the anchor.

Qualification: the main CI run that built these archives passed every job: the shared portable checks, the portable suites on Ubuntu with Node 22 and 24 and on macOS with Node 24, the native addon on linux-x64 and on darwin-arm64 with its suites on Node and on Bun and the Chrome browser/native WebRTC test on Node, and the pack/install smoke of all five archives. No paid hosted run has exercised 0.9.0: `place` and `follows` were measured only on `ReactorTest`, Reactor simulated in memory, so the figures under Added come from a simulation of the-show's air, not from hosted H3. A provider `Started` event is not proof of encoded output.

### Added

- `Playout.place({ key, seconds, continuity, submitIn })` projects where a clip would land if the caller submits it `submitIn` from now, before the caller writes it: the clip it would follow, the clip projected after it, when it would start, how to submit it, and whether that rests on clips already Ready, on projected builds, or on no measured build. It runs the plan forward at the median build rates, from what is queued, building and Ready, the build slot, filler refills and a renewal, and answers the first boundary the clip could make whose submission its lane would take without dropping one made already. With nothing submitted after the call, the clip airs where `place` said, and on the simulated Reactor with fixed build times it starts within 100 ms of `startsAt`, or 150 ms across a renewal, when the lengths ahead were asked for before; else up to a step of H3's grid (0.7 s) more for each clip ahead at a length not asked for before. `PlaceProbe` and `Placement` are exported, and the `Playout` service gains `place`.
- `follows` on `ItemSpec` and `InsertSpec` names the clip, an item or a filler clip by its index, that the item must start right after, across a renewal too. The item waits, not airing, until that clip has aired, and is built only while the air ahead of it outlasts its build, or before builds are measured once that clip is Ready ahead of it; autoplay is fenced before its build, so an early end cannot air it before its predecessor, and one not Ready when that clip ends is dropped as `displaced`. A guarded start can wait for one provider command, whose latency `startsAt` does not project. It is dropped with the new `Dropped` reason `displaced` once that clip goes without airing, once another clip starts after it first, as soon as it is projected unable to be Ready by that clip's end, or once it is Ready and would air before that clip. It gets no filler cover, builds independent rather than miss when it continues a clip, and a replacement keeps it. A cutting lane refuses it, as does a `follows` naming the item's own key, a group key, or filler on a playout without filler. In a simulation of the-show's air on the prototype this was built from, 12 shows of 31 minutes with acknowledgements every 45 s on average and writing times from its writer test, `place` with `follows` aired 69% [65-73] of acknowledgements right between the clips they were written for, and none after another clip, against 43% for an estimate from `state` with a firm window, both with this release's fixes. The clip after one stayed a guess: in a quarter to a third of cases it was a line queued after the call.

### Changed

- The coordinator HTTP client is named `CoordinatorClient`, and transport schemas `Track`, `Mapping`, `IceServer` and `IceCandidate` belong to `Peer`, so browser and native hosts implement the transport without importing the HTTP client.
- An insert after an `At` item takes its time but not its `late`: past that time it airs at the next boundary. Before, a clip inserted after the first beat of a line was dropped when that line's staleness bound passed, though it was not that line. An insert before an `At` item still takes both, since it airs no later than that item.

### Fixed

- An insert made again under its key, with the same spec and anchor, once that anchor had aired, was refused with `InvalidItem` instead of answered with its handle, as keys promise. A caller retrying an insert whose first attempt landed took the refusal for a miss.
- A firm item was dropped `late` at a boundary although it would have started before its `startBy`. Right after a clip ends, H3 answers the end with the facts it held before it, still naming that clip as playing, until its next state and queue reads agree. Meanwhile the playout counted the ended clip's whole length again, so it projected what airs next a clip too late: a firm item waiting to build was dropped, and a firm submission could be refused with `WouldMissDeadline`. In a simulated run of an application's programme, 26 of 589 firm submissions were dropped this way, each exactly on a boundary. A clip seen to end, or to fail on air, now leaves nothing to count. The runway in `state.runwaySeconds`, filler, what fits before a session's cap and cuts read the same count: before, a cut-lane item Ready in the last second of a lower-lane clip started a cut of that clip once it had ended, turning autoplay off at the boundary.
- `ReactorTest`'s H3 went on naming a clip popped in its seam, armed but not yet started, as playing. With no other clip Ready, the seam's end started nothing and sent no state, so a playout took the popped clip as playing for good, and during a renewal the air stayed dark until the retiring session's cap. Popping an armed clip now leaves the air as a boundary does: the state names nothing playing, and the next Ready clip is armed and starts after a seam of its own.

## [0.8.0] - 2026-09-29

0.8.0 rebuilds the SDK the way Effect's own packages are built, and breaks the 0.7 API throughout, so a `^0.7.0` range does not include it. The client is flat modules, each exported as a namespace from the root and as its own subpath: `Reactor`, `Session`, `Coordinator`, `H3`, `Playout`, `H3Source`, `LocalSource`, `Media`, `Peer`, `ReactorError` and `ReactorTest`. One `Playout` service replaces the orchestration engine, renewal and scheduler, which each held part of one plan. `ReactorTest`, Reactor simulated in memory at the network edge and driven by the Effect clock, replaces the simulation, `test-kit`, the loopback twin and the test fixtures. The browser and native packages only bind the client's `Peer` port, and the native addon is a napi-rs module shipped in one package per platform.

Why: 0.6.0's core hand-rolled what Effect provides (a PubSub, a JSON walker, a protobuf runtime, an HTTP wrapper, 100 ms polling loops) inside classes of mutable fields, threw its own errors and caught them again, kept hidden authority in module-level registries, published its internals as `/host` and `/wire`, and was tested through four harness styles over about nine coordinator fakes, while the simulation reported facts hosted H3 never produces. An audit against all of Reactor's documentation, not only H3's schema, then changed the session rules: a session outlives its token, is uncapped unless asked, and reads `INACTIVE` while it is still live.

Upgrading from 0.7.0: import modules by their new names, give sessions `Tokens` instead of a JWT, and move scheduling onto `Playout` with `H3Source` or `LocalSource` as its source and `ReactorTest` for tests. Every public name 0.7.x exported that 0.8.0 removes or renames:

- Sessions outlive their tokens. `Reactor`'s `create` and `attach` take `Tokens`: a token that creates the session, then tokens bound to it (`resources.sessions.bind`), minted a minute before the current one expires, or a quarter of a shorter token's life, with one mint shared by concurrent calls. `coordinator.tokens` builds them from the API key, `fixedTokens` serves a session shorter than its token, and `mintToken` takes `bind`, `maxSessions` (1 to 500) and a cap or `"unlimited"`. A failed refresh is a `Diagnostic` event while the current token still works.
- Content moderation: a `Moderation` session event with the verdict's `action`, `categories`, `inputKind`, `command` and `requestId` when Reactor names them, the `Moderated` code for a terminated session, which is never reconnected, and `Playout`'s `Moderated` session event, `Failed` reason `Moderated` and `maxModerations`.

It models tokens and binding, the API key as a bearer on reads and deletes, several connections per session, the 30 s `INACTIVE` window, Reactor's default quotas (`concurrentSessions`, `sessionsPerMinute`), H3's documented limits, a `stop` that lands after its reply, a moderation verdict `Timing.moderation` after the enqueue, recordings when `recorder` is set, and per-second billing.

A request outside H3's documented limits is refused at admission with `InvalidItem`, its metadata counted as it will be sent, wrapped with the item's key and H3's own identity, so nothing the enqueue would refuse is admitted. `state.playing` names the clip on air, when its start was seen and its length; `events` reports each filler clip's start and end (`Filler`), a dropped connection and its return (`Reconnecting`, `Reconnected { afterMillis }`), and a reader of a session's video or audio that fell behind (`ReaderOverflow`, with the session's `MediaPressure`). `state.runwaySeconds` is the air secured, on the session on air and then on its replacement. An item handle's `started` resolves with its start or how it settled without one (`Playout.NotStarted`), and its `outcome` with how it settled (`Playout.Settled`), so neither needs a case for a status that cannot settle it. `Source` states what the playout relies on from a source, and the playout refuses a source whose session id is already open; a clip id need name only one clip of its own session.
- `Reactor.Options.reconnectTimeout`, 30 seconds by default, the time Reactor keeps a session with no connection; before, a reconnect had the whole `connectTimeout`. `resumeTracks: false` leaves a connection's received tracks paused.
- A session reconnects a dropped connection on its own. `Reactor.Options.reconnect` is the `Schedule` it tries again on, which sees each failure; by default the second attempt comes 250 ms after the first fails and each wait doubles to at most 4 seconds, jittered, and never sooner than a refusal's `Retry-After`, from which it is jittered only upward, all within `reconnectTimeout` of the drop. A schedule with no delay of its own tries again at once for all of `reconnectTimeout`. Owned and attached sessions reconnect, whoever reads them; each attempt is a new generation of the same session, allocates nothing and never replays a command. Nothing reconnects a session that is closing or that Reactor or moderation ended, nor one whose protocol Reactor refuses (`VersionMismatch`); a refusal that may lift, a 401 or 403 included, is tried again, with a fresh token only from its `Tokens`, once the current one nears its expiry. A reconnect counts only once its connection has stayed ready 10 seconds. A connection that drops sooner is a failed attempt of the same reconnect, tried on the schedule and within `reconnectTimeout` of the first drop, so a session whose connections keep dropping stops trying 30 seconds after the first drop, or, if a connection is up then, once that connection drops before it has been ready 10 seconds, `disconnected` with a `Timeout` `lastError`, and Reactor ends it 30 seconds later, rather than being reconnected at once, indefinitely. Each failed attempt is a `Diagnostic` event, and the `Timeout` keeps in its `Redacted` `context.detail` the last attempt's failure, or why the connection up as the time ran out dropped. `Snapshot.reconnecting` is true while the session tries; `disconnected` without it is lasting, from the drop on when no attempt could get past what ended the connection, and `lastError` says why. While the session reconnects on its own, `session.reconnect` joins that reconnect rather than begin another: it succeeds once a connection is ready again, and fails as the reconnect stops, with the session's `lastError`, or with `Closed` if the session closes first. So does a `session.reconnect` whose connection is replaced while it makes its peer: it succeeds once a later connection is ready, and fails with the session's `lastError` once a later one is down for good, as the session's own reconnect stops or as another reconnect asked for fails meanwhile. One that finds another reconnect asked for under way fails with `InvalidState`. The reconnect runs with the tracer, `ErrorReporter`s and clock the acquisition ran with, and each attempt's `Session.reconnect` span begins a trace of its own, linked to the acquisition's. Reconnecting keeps a session billing through its drops, an owned one its application never closed and one a viewer holds after its owner has gone included, for as long as the process holding it lives, to its cap if it has one; `reconnect: false` leaves a dropped connection to `session.reconnect`, and Reactor ends the session 30 seconds after its last connection drops.
- A connect, attach or `session.reconnect` that the session's close overtakes before it takes the session over, or once its connection is open and becoming ready, fails with `Closed`, outcome `not-submitted`, rather than returning or reconnecting a session already closing, and so does a `session.reconnect` asked for once the close has begun, which 0.7.1 refused with `InvalidState`. One the close overtakes earlier in its negotiation fails with `Aborted`, as the close fails its connection. An acquisition's `not-submitted` describes the step that failed, and its `AcquisitionFailure`'s close report says what was allocated.
- `Session.changes`, the snapshot at every change in order, to a reader that falls behind too; `H3.Provider.changes`; and `Coordinator.Rate.per`, the unit a model's price is stated in.
- `H3.Submission`, `H3.SubmissionState` and `H3.CommandName`, the types `prepare` and `Contract` already used.
- `Session.mayStillBill`, whether the session a `CloseReport` closed may still bill: this process owned it and no read confirmed it ended, or its allocation's outcome never arrived. `playout.cleanup` keeps every such report.
- `reactor-effect-native-linux-x64-gnu` and `reactor-effect-native-darwin-arm64`, one package per platform addon, which `reactor-effect-native` pins as exact optional dependencies.

### Changed

- **Sessions are uncapped unless asked, and a creating token must say so.** A token that creates sessions needs `maxSessionDuration`, a duration or `"unlimited"`, and need no longer outlive its session. The grant is read from Reactor's documented `/tokens` echo, not the JWT's claims: an echo wider than asked is refused, and a narrower one is the cap `TokenGrant.maxSessionSeconds` reports. A playout renews on a schedule only a capped session; an uncapped one is replaced when it is lost.
- **A server holding the API key reads and ends any session:** `coordinator.terminate`, `inspect` and `downloadClip` send the key when no `credential` is set, still only to the API's own origin.
- **Any HTTP 5xx is retryable**, as Reactor classes a server error, where only a 503 was; the outcome still decides, so an `unknown` one never is.
- **Connection failures are classified once, by the session, for both hosts,** from the peer's statistics under a 2 s deadline: `TransportFailed` when a candidate pair worked, `IceFailed` when none did, `Disconnected` when the read fails. The browser's `failed` state was `Disconnected` before, and both classified reasons now carry the generation.
- **Control messages are the library's own.** The `Control` event carries `Session.ControlMessage`, whose clip-failure reason and error text are `Redacted`, instead of the wire message, and a `clip_ready` its Schema refuses fails its request as `Protocol`.
- **Every failure after an allocation carries its cleanup report.** An `onAllocated` hook may fail with its own error: the session is closed, and the acquisition fails with an `AcquisitionFailure` whose `cleanup` is the close report. One of the client's failures keeps its reason and context, any other error becomes `Aborted` with the hook's error in the `Redacted` `context.detail`, and a defect stays a defect, raised once the session is closed. `Reactor.create` and `H3Source.open` fail with `AcquisitionFailure` alone.
- **H3 lets the queue decide an enqueue whose reply stays away.** H3 lists a new clip before it replies, so an enqueue whose reply is lost after its clip was listed is decided by that listing once `reconcileWindow` (5 s) has passed, rather than at the 15 s reply deadline; nothing is sent again.
- **A defect stays a defect.** A defect in a connection's heartbeat or ICE task ends that task, where it failed the connection as `Protocol` ("session task failed") and invited a reconnect. A defect that stops the playout, such as a throwing `filler.clip`, is the defect `playout.failure` dies with, and its text never enters a message. The playout hands every defect it catches, from its plan, an open, a source's events, a command or a close, a defect that rides beside a failure included, to Effect's `ErrorReporter`, a `Source` method that throws when called included. The playout takes whether that command applied as unknown and goes on: it never sends an enqueue again, asks again for a `remove` once the session's queues change and for a `move` a second later, sends the autoplay it wants again, a second later if that is the value that died and at once if not, sending that session nothing else meanwhile but the removal of its filler as it retires, and ends a `stop` or `play`'s cut.
- **H3 needs only `enqueue`, `get_state` and `get_queue`** to start on a deployment, where it refused one missing any of its thirteen commands; a method whose command the deployment lacks fails `UnsupportedCapability` before anything is sent.
- **The playout differs from 0.7.0's scheduler in these ways:**
  - A renewal switch always waits the grace after the retiring session's last clip left the air, by ending or by failing there; it no longer switches early on a complete frame count, and `Switched.decision` is `no-observed-start` or `grace-elapsed`. A filler clip that fails on air is reported `Ended` in `events`.
  - An enqueue whose outcome stays unknown past `unknownTimeout` (60 seconds) makes its session indeterminate, so a replacement takes over, where 0.7.0 failed the whole scheduler with `Timeout`. Meanwhile it holds no build slot, so what follows builds behind it.
  - `video` and `audio` are streams of the on-air session, read as the application likes, and end when the playout stops. Media pressure, loss totals, `MediaState` and mandatory consumption are gone; a reader that falls behind reads again from the next frame, the host counts the loss in `readerOverflows`, and `events` reports it as `ReaderOverflow`, naming the session and track.
  - `playout.cleanup` is one record, `{ sessions, retained }`, holding every close report whose session may still bill (`Session.mayStillBill`), a failed open's included, and the latest eight others, in place of `CleanupReport` and `CleanupSummary`.
  - There is no session cap and no raw engine command: the canvas is an `H3Source` option, references are bytes or uploads, and `firstDecisive` is `started`.
  - Reconnecting is the session's business: a session reconnects a dropped connection itself, and `H3Source` follows it once in its own scope, whoever reads its events. It gives the session `recovery` (20 seconds) to be ready again, reads H3 afresh, and reports the drop and the return through `Reconnecting` and `Reconnected` session events; a session that will not come back, with `reconnect: false`, once moderation ended it or once it stops trying, is lost at once, with no `Reconnecting` before the loss. A connection that drops again while the source reads H3 on it after a reconnect is waited out within the same `recovery`. The playout sends the session nothing meanwhile. An enqueue the session refused unsent, not ready for it, is sent there again once what the session reports has changed, never on a timer, and fails with its `Command` reason only if refused again while the session reports itself ready.
  - A cut is a step at a time, each sent once the last has landed: autoplay off, `Source.stop(clipId)`, which names the clip to stop and completes once its end is reported, then `Source.play(clipId)` for the cutter, and autoplay back on. The plan looks again between them, so a cutter withdrawn while the stop lands is removed, never played, and its withdrawal answers `withdrawn`. On the wire a cut is still one `stop` before the cutter starts. A source may report a `PlayingClip` whose tag and length are unknown, such as one playing before a resumed source attached.
  - A capped session builds only what airs before its cap, and what would not fit waits for the replacement, which opens `lead` before the cap as 0.7.0's did; end cues count from the provider's length; `withdraw` never fails, answering from how the item settled, or once the playout has stopped from what became of it; a group key's withdrawal answers from its parts, as 0.7.0 did, `withdrawn` if any part was and otherwise `already-started` if any started.
  - A renewal that cannot open no longer ends the air. Each open is retried a second longer after each failed setup, a session lost before any clip sent to it started included, but at most `maxSetupFailures` (3) seconds later, and never sooner than a refusal's `Retry-After`, where 0.7.0 waited 5 seconds. An open refused with nothing allocated, such as with a 4xx, billed nothing: refused while a session holds the air, it counts toward `maxSetupFailures` neither then nor later, and it is asked again however often it is refused. A run of failed setups ends only when a session airs its first clip, not at each clip the session on air starts. Once that many that count have failed in a row while a session holds the air, opening pauses until that session's cap ends it or it is lost; then one more open is tried, once the last failure's delay and `Retry-After` have passed, and the playout fails only if that one fails too. 0.7.0 failed with `Disconnected` after the third.
  - Each session's provider commands go one at a time on a lane of their own, and sessions' lanes run side by side, where 0.7.0's scheduler sent one command at a time across all of them. An enqueue whose command is lost, which holds its lane for the reply timeout and the reconcile window, about 20 s, now holds up only its own session, a filler clip's included: in a renewal, an item submitted once the replacement opened was Ready 2.2 s later, where it waited 17.2 s, and with a filler enqueue lost on the session on air, the replacement sent its first filler clip 0.7 s after it opened. Each filler clip takes its index as its enqueue goes out, and one the provider refused is asked for again as it was, on whichever session's lane is free.
  - `H3Source.open`'s lifetime is what remains of its cap when it returns, counted from the allocation request, so the playout never plans past the session's end. On a host without decoded media, `H3Source`'s `video` and `audio` fail with `UnsupportedCapability`; only a retired connection generation's end is quiet.
  - `H3Source.resume` sets `flush_on_clip_end` only when the session has it otherwise, so adopting a session its owner set up sends only reads.
  - A filler request outside H3's documented limits fails the playout with `Playout.InvalidFiller`, naming the filler clip's index, where 0.7.0 had it refused and asked again every second.
  - Filler builds are measured as items' are, so a playout airing only filler learns its build rate (`state.estimates.build`), and its filler floor then covers one p95 build.
  - Filler protects the air before queue order by default (`filler.protect: "air"`). Once three builds were measured, an item whose p95 build, at the continued rate if it continues a clip, would outlast `state.runwaySeconds` waits for one filler clip that builds sooner than it does, long enough within `lengths` to cover the rest and a second more, and airing no longer than the item builds unless `lengths.min` is longer; the floor, which filler refills without holding any item, covers the next such item's build and a second more. An item waits for one such clip at most, and once more on a session it is carried to. One with a time to meet goes at once: one with an `At` start or a `startBy`, and, as its time is now, one with an `Asap` start, a released `Manual` one, or one on a lane that cuts. At the simulated hosted speeds, a 15 s continued item submitted on 10 s of filler runway left the air dark for 6.4 s; it now leaves none and airs about 8 s later. `filler.protect: "order"` builds each item as soon as it may, as 0.7.0 did.
- **Moderation is bounded.** A clip lost before it was built, with two sessions in a row, fails, since a verdict need not come; a session lost before any clip sent to it started counts as a failed setup.
- **A local renderer's hooks are Effects, and each clip owns what they make.** `LocalSource.open({ build, present })`: `build` returns a clip's value and, when it differs, its built length (`LocalSource.Rendered`), and `present(clip, value, sink)` plays that value. Both run in a scope the clip owns, which closes once the clip leaves the source, so its finalizers release what the hooks made. Each hook fails with its own error and needs its own services, and the source needs both hooks' services. A hook that fails with the application's own error fails its clip alone, reason `Clip`, the error `Redacted` in `provider`; one that dies stops the source, its `events` die with the defect for every reader, and the playout replaces the session. A source's session id is `local-` and 14 random hex digits, so the two sources a renewal holds at once differ.
- **Spans are named `Module.operation`:** `Reactor.create`, `Session.command`, `Coordinator.terminate`, `H3.enqueue`, `Playout.submit` and so on, where 0.7.x had `reactor.session.create`, `reactor.coordinator.terminate`, `reactor.h3.enqueue` and `Scheduler.submit`; `H3Source.open` and `H3Source.resume` too, and attributes keep their `reactor.*` names.
- **The wire codec is protobuf-es, generated by `buf`.** A message above 256 KiB, or one protobuf-es refuses, is `Protocol`, protobuf-es's 100-message nesting limit replaces the old depth and field budgets, and a received Struct holding `NaN` or `Infinity` is a `Protocol` failure.
- **The native addon is a napi-rs module.** It replaces the C ABI loaded with Koffi: calls return promises of typed replies, and a readiness bit wakes the host through one non-blocking threadsafe function. It ships in the platform's own package, which must match `reactor-effect-native`'s version: a host without one fails `NativePeer.layer()` with `UnsupportedHost`, a mismatched one with `Native`. A refusal before a call ran (`InvalidInput`, `Overflow`, `Closed`, `ChannelClosed`) is `not-submitted`, and every other class `unknown`. Each reader now holds 24 video frames, a second at 24 fps, where it held 4. An owner join that outlived its deadline is held by the layer that made the peer, not by the process.
- **Tooling:** Python leaves the toolchain, since `buf` from `bun install` generates the wire codec; every `@effect/tsgo` rule is an error in every file, and lint reports unused suppressions; every suite in the workspace runs under Vitest with `@effect/vitest`. The hosted qualification is `integration/hosted/main.ts`, rehearsed on `ReactorTest` in CI, and 0.8.0 starts a new ledger in its v2 evidence schema; the integration runner needs Node 22.18 or newer.
- **The Effect peers are exact again:** `effect` `4.0.0-rc.117` for every package, and `@effect/platform-node` and `@effect/platform-node-shared` `4.0.0-rc.117` for `reactor-effect-native`, where 0.3.3 through 0.7.1 accepted any later rc through `^4.0.0-rc.117`. Effect `4.0.0-rc.118` moved every `effect/unstable/*` module into `effect/*`, so a fresh install of 0.7.1 took rc.118 and failed to import `effect/unstable/http`. The shared platform is a peer because `@effect/platform-node@4.0.0-rc.117` depends on `^4.0.0-rc.117` of it, and npm would otherwise install rc.118 beside it, whose `NodeServices` fails to load on Effect rc.117. An application that adds `@effect/platform-node` itself should install it with `--save-exact` and, without `reactor-effect-native`, pin the shared platform with its own override, as the client's README shows. The pack check now also installs the client as an application does, letting npm take Effect through the published peer, and imports every module on Node.

### Removed

- The `orchestration`, `simulation`, `testing`, `wire` and `host` entries, `test-kit`, the loopback twin and the Python wire generator. The tables above name every public export that went and what replaces it.

### Fixed

- A session whose last connection dropped reads `INACTIVE` on hosted Reactor, and it is still live: it runs, and bills, for 30 seconds until a connection returns. 0.7.x counted it as ended, so adopting it failed with `TerminalSession`, as the first paid `tokens` run showed. Only `CLOSED` is terminal now: adoption, resume, reconnect and the ready poll accept an `INACTIVE` session, and termination is confirmed only by `CLOSED` or absence.
- A create answered with a 5xx was taken as proof that nothing was allocated. Only a 4xx refusal proves that, so a server error now fails the create with outcome `unknown`, its allocation unknown and not retryable.
- A command's error reply put the provider's code into the failure's message, which logs, spans and `toJSON` show. The message is now "remote command error", and the code is in the `Redacted` `Remote.remoteCode`.
- The H3 provider failed as `Protocol` on a `state_update` whose `playing` and `playing_clip_id` disagreed, a combination H3's documentation leaves open for an armed clip. It is accepted now.
- Filler tiling the gap before an `At` item asked for less than its share, by the actual-over-requested ratio learned on 5 s clips, which H3's frame grid does not follow: in the hosted `show` rehearsal a 6 s gap got a 5.806 s request that aired as 5.875 s, the 125 ms left cost a whole 5 s filler clip, and the item aired about 5 s late. A tile now asks for its share, which H3 only lengthens, and asks for more only from a provider that shortens clips.
- `downloadClip` failed with `TerminalSession` as soon as a pending recording's session had ended, though Reactor keeps a recording for 24 hours and it can finish after its session. It now waits for the playlist until the clip's predicted ready time and 10 seconds more.
- A reconnect goes on when the connection it replaces fails to shut down, as a native peer does once its owner join outlives `shutdownTimeout`: the host's failure is a `Diagnostic` event on the replaced generation, and any other defect goes to the `ErrorReporter`. Before, the session stayed `connecting` for good, `session.reconnect` in 0.7.1 included.
- A connection whose host dies as the session fences its peer, or whose sent track's `stop()` throws, now leaves the session `disconnected`, reconnecting on its own if it does, as any drop does. What the host died of is a `Diagnostic` event if it is a `ReactorError`, and any other defect goes to the `ErrorReporter`; at the session's close it is kept in the `CloseReport`'s `localErrors`. Before, the session stayed `ready` on a dead connection and nothing reconnected it, 0.7.1 included.
- `session.reconnect`, `Reactor.create` and `Reactor.attach` fail with the attempt's own failure alone. What the host dies of as it shuts down that attempt's peer is reported the same way. Before, it rode in the failure's cause beside that failure, where `Effect.catch`, `Effect.flip` and `Effect.retry` dropped it unseen, and a `session.reconnect` overtaken by another attempt died of it rather than failing with `InvalidState`.
- A connection attempt's deadline could tear down a connection it had already reported `ready`: the negotiation resumed the received tracks, applied the bitrates and started the heartbeat after the move to `ready`, still inside the deadline, and a deadline that passed then failed the new connection. 0.7.1 did the same inside its `connectTimeout`. The move to `ready` is now the negotiation's last step, and readies the session only while that connection is still its own and up, so a connect, attach or reconnect whose connection drops during those steps fails with that drop, where 0.7.1 reported it ready and then dropped it. A `create` or `attach` that fails so closes its session, terminating one it owns or adopted, an `H3Source.resume`'s included.

## [0.7.0] - 2026-09-27

The orchestration scheduler becomes a queue a live show can edit. Beats of a line air back to back as a group. A queued beat can be replaced, and a clip inserted before or after any beat. Drops, amendments and inserts apply together as one make-before-break batch, where the old beats cover until the new ones are Ready. Lanes can replace or skip, or cut lower lanes. Items can start as soon as possible or be held until released. Cues fire at offsets from a clip's start or end. Clips lost with a session are rebuilt from the plan, filler lengths tile the gap to an anchor, and a clip can continue from the one before it. Deadlines and the runway floor now use build times the scheduler measures itself, and refused withdrawals are retried by the scheduler. `SchedulerShape`, `EngineShape`, `StartMode`, `AsRunStatus`, `SchedulerState` and the submission errors gain members, so a `^0.6.0` range does not include it. The native Rust sources are unchanged.

Upgrading from 0.6.0:

- A hand-written `EngineShape` needs `cut(clipId)`, and a hand-written `SchedulerShape` needs `submitGroup`, `replace`, `insert`, `edit`, `release` and `cues`.
- An exhaustive switch over `AsRunStatus` must handle `Dropped` with reason `replaced`, and over `StartMode`, `Asap` and `Manual`. `Accepted` may carry `carried`.
- `submit`, `submitGroup` and `edit` can fail with `LaneBusy`, but only for a lane configured with `conflict: "skip"`.
- `withdraw` no longer fails on a provider refusal, so an application's own retry of refused withdrawals can go. An unknown removal still fails the call.
- Filler now refills when the runway falls below its floor. Before, it refilled at every clip boundary, whatever the floor, because the runway briefly read zero. A nonzero floor is also raised to one measured p95 filler build plus a second. A floor tuned around the old behaviour may deserve a second look.
- Once three builds are measured, `WouldMissDeadline` also counts build time, and a firm item that can no longer make its deadline is dropped as `late` before it is built, rather than at its deadline.

Qualification: the main CI run that built these archives passed the portable suites on Node and Bun, the native build and suite on linux-x64 and darwin-arm64, and the pack/install smoke of all three archives. The scheduler changes have run only against the simulation and scripted engines, including a regression test for each of the 15 defects an independent review found in them. On hosted H3, `move` and `pop` of a waiting clip, the queue edits all of this builds on, decided the next clip down to 160 ms before `clip_finished`, with no pause at the seams, in 0.6.0's paid `scheduler` run. Inserted clips' pose joins, continuity, a cut's seam and a batch landing at one boundary are unqualified there. A provider `Started` event is not proof of encoded output.

### Added

- `Scheduler.submitGroup` submits a group of parts that build in order and air back to back, such as the beats of one line, with a handle per part. A deadline can move a whole group ahead in its lane but never split one, and a group that has started keeps its remaining parts ahead of the rest of its lane; a higher lane can still go in between parts. `withdraw` takes a group key for every unstarted part, or a part key for that part and the parts after it, and a part that fails or is dropped withdraws the parts after it. `GroupSpec`, `GroupPart` and `GroupHandle` are exported. `SchedulerShape` gains `submitGroup`, so a hand-written implementation of it needs one.
- `Scheduler.replace(key, { key, request })` amends a queued item or group part make-before-break. The new clip takes the old one's place and builds first in its lane; once it is Ready the old one is withdrawn as `Dropped` with the new reason `replaced`. If the old one starts first, the replacement is withdrawn instead. `ReplacementSpec` is exported. `SchedulerShape` gains `replace`, and `AsRunStatus`'s `Dropped` reason gains `replaced`, which a switch written to be exhaustive must handle.
- `Scheduler.insert({ key, request, before | after, window })` places a clip immediately before or after an item, a group part or a group, in the anchor's lane, for example an acknowledgement at the next boundary (`after` the playing clip) or before a given beat. Between two parts of a group it joins the group so the group stays together, but its own failure or withdrawal never breaks the group. An insert that misses its place airs at the next boundary. `InsertSpec` is exported, and `SchedulerShape` gains `insert`.
- `Scheduler.edit([...])` applies submissions, groups, inserts, replacements and withdrawals as one change, as the-show's queue edits need: an acknowledgement and the drops or amendments an event calls for land together, and a whole plan can be replaced. Every edit is checked first, so a refused one fails the batch and admits nothing. The batch is make-before-break: what it withdraws airs only as cover, after anything the batch adds that is Ready, until everything it adds is Ready or has settled; then its withdrawals and replacements are requested together. An item nothing was built for goes at once. The handle reports one result per edit and a `committed` effect. `Edit`, `EditResult` and `EditHandle` are exported, and `SchedulerShape` gains `edit`.
- The scheduler measures its provider as it runs: each build from sending it to its clip being Ready, per requested second, and each clip's actual over requested length. `SchedulerState.estimates` reports the median and p95 build rate once three builds were measured, and the length ratio. With them, `WouldMissDeadline` also counts the clip's own build and the builds that must go before it, a firm item that can no longer start before its deadline is dropped as `late` before it is built, and a nonzero runway floor is raised to one p95 build of the next filler clip plus a second, so filler started at the floor is Ready in time. `SchedulerState` gains `estimates`, which a hand-built state value needs.
- Scheduler lanes take a conflict policy and may cut, the per-lane policies research report C proposed (UMIM's replace and skip, and cut lanes). `LaneSpec.conflict` is `"queue"` (the default), `"replace"`, which supersedes the lane's waiting items make-before-break and settles them `Dropped` as `replaced`, or `"skip"`, which refuses a submission with the new `LaneBusy` error while the lane has an item waiting or playing. `LaneSpec.cut` lets a Ready item cut a playing clip of a lower lane or filler, unless it ends within a second, through the new `EngineShape.cut(clipId)`, which stops a clip only if it is still playing. `submit`, `submitGroup` and `edit` can fail with `LaneBusy`, and a hand-written `EngineShape` needs `cut`. A cut on hosted H3 has not been qualified.
- Two start modes beside `Follow` and `At`, from research report A's common set: `Asap` airs at the next boundary ahead of everything waiting in every lane and builds first, and `Manual` is built ahead and held until the new `Scheduler.release(key)`, which sends it to the next boundary as `Asap`. A held item is built early only while filler keeps the runway at its floor, and one that would still be next at a boundary is removed and rebuilt; with filler off it is built once released. `StartMode` gains both, which an exhaustive switch must handle, and `SchedulerShape` gains `release`.
- Secondary events, from research report A: an item, group part, insert or replacement carries `cues`, each named and timed from its clip's observed start or back from its end, and `Scheduler.cues` publishes them as they fire, within 100 ms, while the clip plays. A cue due after a clip was cut never fires. `Cue` and `CueEvent` are exported, and `SchedulerShape` gains `cues`.
- The scheduler rebuilds from its plan after a session is lost, as research report A recommends for a replacement session: an item whose clip was queued, building or Ready on a session that renewal replaced, and so never aired, is rebuilt on the replacement under the same key instead of settling `Failed`. As-run records it `Accepted` again, with `carried: { sessionId }`. A clip lost while playing still settles `Failed`. Renewal marks a clip lost with its session with the new `lost: true` on the engine's `Failed` event.
- Filler sized to the gap, from research reports A and B: the filler callback's `FillContext` gains `durationSeconds`, a suggested requested length. Before an `At` anchor it tiles the uncovered gap in equal clips within the provider's lengths, adjusted by the measured length ratio, so filler ends on the anchor; otherwise it is the shortest length, which keeps boundaries frequent. `filler.lengths` bounds it and defaults to H3's 5 to 15.084 second request range.
- `continuity: "previous"` on an item, group part, insert or replacement builds its clip continuing from the clip that airs just before it, for the pose and motion joins the-show's queue edits ask of an inserted or amended beat. The scheduler resolves that clip at build time, waits for it to be built, and builds independently when there is none or the provider no longer offers it; such a clip takes at most two audio references.

### Changed

- The hosted `scheduler` and `scheduler-renewal` checks' first paid runs, against published 0.6.0, are committed in `integration/hosted/evidence/0.6.0/`. `scheduler-renewal` passed; `scheduler` failed only its position-zero criterion, an ordering fault in the check itself, and showed moves and pops deciding the next clip down to 160 ms before `clip_finished` with no pause at the seams.
- `WouldMissDeadline` now counts only the Ready clips that rank ahead of the new item's place, so a Ready clip held for a future `At` anchor no longer counts against a submission.
- `Scheduler.withdraw` no longer fails when the provider refuses a removal or the removal is not sent, for example while a source recovers. The scheduler keeps the withdrawal and retries it a second after each refusal, until the clip is removed, starts or settles another way, so an application no longer retries withdrawals itself. A withdrawal whose item fails while it is being retried replies `not-found`. An unknown removal outcome still fails the call, because the removal may already have taken effect.
- Every removal the scheduler decides for itself (a firm deadline or `At` anchor missed, a broken group, a replacement taking over or losing its race, a drain, and filler at a renewal handoff or a drain) now comes from its pure policy, beside build admission and Ready ordering. Several late items are withdrawn in one pass rather than one per pass.

### Fixed

Engine state can show the next clip playing before the scheduler handles its Started event, and for that moment the runway read zero, which started a refill at every clip boundary whatever the floor. The runway now uses the engine's own start observation, so filler refills when the runway actually falls below the floor.

## [0.3.2] - 2026-09-25

Adopting an attached session and resuming a recorded H3 session, added to the 0.3.1 API without breaking it. The native sources are unchanged since 0.3.0, and `reactor-effect-native` is released with the client as always.

Qualification: the main CI run that built these archives passed the portable suites on Node and Bun, the native build and suite on linux-x64 and darwin-arm64, the Chrome browser/native WebRTC test on each, and the pack/install smoke of all three archives. It ran the twin test in which a killed owner's session resumes through an orchestration whose close terminates it, and rehearsed the new hosted `resume` check against the twin. That check has not run against hosted Reactor.

### Added

- `AttachOptions.adopt: true` takes an attached session's remote lifetime over. The session is `owned`, so closing it, or a failed `attachConnected`, terminates it and confirms the end, and its `CloseReport` says `ownership: "owned"`. Without it an attach still never terminates the session it joined. The attach span records `reactor.session.adopt`.
- `Orchestration.Allocation.endsAt`: when the session's granted length ends at the latest, in seconds since the epoch, taken from just before the create request so it is never later than the server's end. `openH3` sets it; it is optional in the Schema, so a 0.3.0 record still decodes.
- `Orchestration.resumeH3({ allocation, jwt, source? })` resumes a paid H3 session that `openH3` allocated, after its owner died: it attaches with `adopt: true` and derives the session's source, with the time left until `endsAt` as its lifetime, so it is a renewal `open` and renewal terminates the session when it retires it. It sends no policy command a playing session refuses: the session keeps its canvas (the source options take no `canvas`), queue and playback, and only `holdLastFrame`, which H3 accepts at any time, is applied. A record without `endsAt`, for another model or past its end is refused before anything is sent, and a failure after attaching terminates the adopted session and reports it in the `AcquisitionFailure`. It runs in a `reactor.orchestration.resume` span.
- The hosted qualification gains a `resume` check: the takeover, with the new process resuming through `resumeH3` and ending the session by closing the resumed source. It has not run against hosted Reactor yet; the tests and a rehearsal against the twin qualify resume, including a twin test in which a killed owner's session resumes through an orchestration and its close terminates it.

## [0.3.1] - 2026-09-24

H3 reference audio, added to the 0.3.0 API without breaking it. The native sources are unchanged since 0.3.0, and `reactor-effect-native` is released with the client as always.

Qualification: the main CI run that built these archives passed the portable suites on Node and Bun, the native build and suite on linux-x64 and darwin-arm64, the Chrome browser/native WebRTC test on each, and the pack/install smoke of all three archives, and it rehearsed the new hosted `audio` check against the twin. That check has not run against hosted Reactor, so whether the hosted deployment declares `reference_audios` and reports `has_reference_audio` is unverified.

### Added

- H3 reference audio. `H3.Request.audio` carries up to three audio references, as bytes or existing uploads, sent as the documented `reference_audios`: each 2–15 s of WAV, MP3, AAC/M4A, OGG/Opus, FLAC or WebM, mono or stereo, at most 25 MiB. The adapter uploads bytes under the MIME type of their container, content-addressed with the images, and refuses before any upload, `not-submitted`, what H3 documents it would refuse: more than three, more than two beside `continueFrom`, audio with neither an image nor `continueFrom`, more than twelve references in all, and bytes that are no documented container, or a WAV or FLAC whose header gives a length outside 2–15 s or more than two channels. `H3.validateAudioReference` validates one once for reuse, and `H3.audioReferenceLimits` and the profile's new optional `audioReferences` state the bounds.
- `Contract.referenceAudio` says whether a deployment's `enqueue` declares `reference_audios`. A deployment that leaves it out is still admitted, and a request with audio then fails `UnsupportedCapability` before anything is uploaded; one that declares it in another shape, or with fewer than three items, is refused as before for any contract mismatch. A request without audio sends no `reference_audios`, so it reads to a deployment exactly as it did.
- Orchestration `ClipRequest.audio`, `{ uri }` values loaded as image references are, with the same count rules checked when the request is captured. The simulation records a clip's audio in its `has_reference_audio` and `reference_audio_count`, and a simulation whose profile has no `audioReferences` refuses a clip with audio.
- `/testing` exports `wavBytes(seconds, options?)`, a 16-bit PCM tone whose header gives its length.
- The hosted qualification gains an `audio` check, the vertical with a reference image and a reference audio clip, which passes only if the accepted clip reports `has_reference_audio`. It has not run against hosted Reactor yet: reference audio is qualified by the tests and a rehearsal against the twin, which now also refuses more than two audio references beside a continuation and more than twelve references in all, as H3 documents.

## [0.3.0] - 2026-09-24

0.3.0-rc.0 with the three fixes that the hosted qualification found, published to npm's `latest` dist-tag. It breaks the 0.2.0 API: the 0.3.0-rc.0 section below lists every change from 0.2.0, and this section lists those since. The native sources are unchanged since 0.3.0-rc.0 (the same source identity), and `reactor-effect-native` is released with the client as always.

Qualification: on September 24, 2026, the hosted qualification in `integration/hosted` passed its vertical and takeover checks against hosted Reactor, run with Bun 1.4.2 on linux x64 from a checkout of [0255871], the source of this release, with the 0.3.0-rc.0 native library (ABI 4, libwebrtc prebuilt `webrtc-7907-a5ddff60-p9`), from a workstation whose outbound UDP was open. The vertical allocated a session, was ready 2.7 s later, and had its 5 s clip accepted 0.03 s after submission by the correlated `clip_queued` reply; the clip started 2.15 s after acceptance and its first frame came 0.10 s after the start. 124 frames of 1344x768 BGRA arrived at 24.2 fps with none lost, with 48 kHz mono audio, over a direct pair whose local candidate was peer-reflexive; the session's termination was confirmed 0.65 s after its DELETE. The takeover killed the owning process mid-clip: a new process attached 2.69 s later, named the playing clip, found the queued clip's metadata intact, enqueued nothing, received its first frame 0.21 s after attaching, and terminated the session through the durable owner record. The three runs of the published 0.3.0-rc.0 that preceded them failed on the causes fixed below, and every session's termination was confirmed. Main CI qualified these archives as it did 0.3.0-rc.0's. The record, with timings, session ids and the billing reading, is [integration/hosted/evidence/0.3.0-rc.0/summary.md](./integration/hosted/evidence/0.3.0-rc.0/summary.md).

### Fixed

- An attached connection resumes its receive-only tracks when it connects and whenever it reconnects, as a created one does. Reactor holds each connection's media until that connection resumes its tracks, so an attach received no frames. The hosted qualification's takeover found this on September 24, 2026.
- `session.stats` reports the candidate pair that carries the connection. That is the pair a transport names in `selectedCandidatePairId`, as browsers report it, or else the nominated, succeeded pair that received the most since the previous sample. It used to take the first nominated, succeeded pair, but ICE leaves a pair nominated after moving off it. So a hosted session reported a relay pair that carried nothing while its media arrived over a direct one.
- H3: an enqueue is accepted by its matched `clip_queued` reply, with `correlated` evidence, even when a broadcast listed its clip first. Hosted H3 broadcasts the queue before it replies, so every hosted acceptance read `metadata`. Evidence by metadata that arrives while the reply is awaited is now held until the reply is observed. It decides the acceptance only if the reply does not: after an acknowledgement or a lost reply, or when a new transport generation, a provider failure or the provider's close ends the wait first. The clip operation records its clip's facts meanwhile and resolves them once the acceptance is decided; a reply that refuses the enqueue discards both.

## [0.3.0-rc.0] - 2026-09-24

The first release candidate of 0.3.0, published to npm's `next` dist-tag while `latest` stays at 0.2.0: install it with `npm install reactor-effect-client@next` and the matching host package. It breaks the 0.2.0 API, and a `^0.2.0` range does not include it, so applications move to it deliberately. 0.3.0 follows once the hosted qualification in `integration/hosted` has passed its vertical and takeover checks against hosted Reactor; no hosted Reactor generation has been run against this code yet.

Qualification: the main CI run that built these archives passed the portable suites on Node and Bun, the native build and suite at ABI 4 on GitHub's linux-x64 and darwin-arm64 runners on Node and Bun, the Chrome browser/native WebRTC test on each, and the pack/install smoke of all three archives. The media load tests first passed on September 23, 2026, at ABI 3, in a linux-x64 container (Rust 1.90.0, Clang 21.1.8, Node 24.15.0, Bun 1.4.2) and in CI; the README's support section keeps their measured limits, and that record is in the README at [c2e6618]. Against the ABI 2 bridge, the same load tests had failed throughput, stall and renewal on Bun and the two-session test on Node. Getting them to pass on the darwin-arm64 runner took linking the far peer against compiler-rt, holding its congestion controller at a fixed rate and stopping Spotlight during the native job.

### Added

- `EngineShape.observe(options)` and `Source.observe(options)` return an `EngineObservation`: the engine's state and a stream of every event after it, subscribed before the state is read, so no event falls between them. Events may repeat what the state already reflects and are applied by `clipId`; after an `Overflow`, observe again. `Observations.observeWith(state, options)` builds the same pairing for a host's own observations.
- `recorder(stream)` turns one track's frames into every frame it delivers plus a `Lost { after, count }` element wherever the host dropped frames between two it delivered, from their admission sequences; `Recorded` is its element type. A preview keeps using `Stream.buffer({ capacity: 1, strategy: "sliding" })`.
- `provider.operation(submission)` returns a committed submission's `ClipOperation` for as long as its scope holds it: `accepted`, `reached("generated" | "started")`, `ended` and `facts`, each resolved once from the provider's own reducer. A phase completes when it or a later one is observed, from a lifecycle message or a queue or state snapshot, and every `ClipFact` names the transport generation of its evidence; a clip that fails or is popped first fails the phases it never reached with the new `ClipEnded` reason; a definite enqueue failure fails every fact with that failure; and a provider that retires first resolves the rest as `Indeterminate`, a new failure code. A clip carrying the submission's metadata still resolves an unknown enqueue after its reconcile window or in a later transport generation of the same session, without changing `provider.acceptances`. A commit takes one of `maxOperations` slots (1024 by default) before it sends: ended operations are evicted first, and a table of unresolved ones refuses the commit with `Overflow`, not submitted. Releasing the scope acknowledges the operation and frees its slot.
- `Orchestration.openH3({ mint, onAllocated?, create?, source? })` opens a paid H3 session as an orchestration source: it mints the session token (the API key never reaches it), allocates the session with `Client`, runs `onAllocated({ session, grant })` before connecting so the application can record the owner durably (the grant's `jwt` stays `Redacted`), connects, and derives the source with `fromH3Session`. It returns `{ source, lifetime }` with the granted session length as a lifetime in seconds, so it is directly a renewal `open`. A failure after allocation closes the session first and reports its cleanup in an `AcquisitionFailure`; an application error from `onAllocated` is returned as it was.
- Schemas for the evidence the client returns, so an application can persist it without redefining its shape: `CloseReport` and `Termination` at the root (also `Coordinator.Termination`), and `Orchestration.CleanupReport`, `SourceCleanup` and `PolicyCleanup`. Each is also its type. Encode to JSON with `Schema.toCodecJson`. A failure inside a report encodes as its diagnostic JSON (`toJSON`), so provider text (`body`), native backend text and `context.detail` never reach the stored form, and decodes back to a failure of the same class without them.
- `Orchestration.Allocation`, a durable owner record `{ sessionId, ownership, model, expiresAt }` without the token, and the `allocation` field of `openH3`'s `onAllocated` argument, which carries it.
- Orchestration options `maxQueuedVideoFrames` and `maxQueuedAudioSamples` set how much undrained media the output keeps before it fails with `Overflow`, 96 frames and 192,000 samples (4 seconds each) by default, as before.
- `Orchestration.layer(options)` provides the `Engine`, `Media` and `Handle` services of one orchestration, as `Simulation.layerSim` does for a simulated one, so the three can never come from two paid session chains.
- `HandleShape.observe(options)` returns the handle's engine and media state with one ordered stream of `HandleEvent`s after it: engine events, `Renewal` events and `MediaState` transitions, in the order they happened, so a `Replaced` follows the `Failed` events of the clips it lost and a media state never arrives out of order. It subscribes before it reads, like `engine.observe`, which is now its projection.
- A span for each operation a caller can cancel: `reactor.session.create` and `attach` (with the model name or attached session id), `reactor.session.connect` and `reconnect` (with the connection generation, session id and an event per phase: `reactor.connect.described`, `prepared`, `registered`, `offered`, `answered`, `ready`), `reactor.session.upload` (MIME type and size only), `reactor.session.close`, and `reactor.orchestration.renewal.open`, `recover`, `replace` and `switch`. An H3 enqueue runs in a `reactor.h3.enqueue` span on the submission's own execution, with its acceptance wait in `reactor.h3.reconcile`. `reactor.coordinator.terminate` and `reactor.session.close` carry the termination verdict as `reactor.termination.attempted`, `confirmed` and `evidence`, because termination reports rather than fails and its span otherwise ends without error even when a paid session was not confirmed stopped. Every span skips stack capture, and none records a credential, input, reply or provider text; the renewal tick, frames and heartbeats are not traced.
- Each dispatched model command and control request runs in a `reactor.session.command` or `reactor.session.control` client span on the session-owned execution. The span is a child of the caller's span and ends with the request's own outcome, even after the caller stopped waiting. It carries `reactor.operation`, `reactor.request.id` and `reactor.connection.generation`, and on exit `reactor.command.outcome` and, for a typed failure, `error.type` set to its reason's tag. It never carries the input, the reply or provider text. A request refused before dispatch opens no span, and heartbeats are not traced.
- The client's failures route on a tagged `reason` with `Effect.catchReason`, `catchReasons` and `unwrapReason`. The reason classes are exported: `Failure`, whose tag is a code such as `Timeout`; `Http` (`status`, `retryAfter`, `body`); `Remote`, tagged `Remote` or `RecorderDisabled` (`remoteCode`, `body`); `Native` (`status`, a Redacted `backendMessage`); `IceFailed` (`pairs`, `candidateTypes`); and `TransportFailed` (`pairs`). `ReactorError.fromCode(code, message, context?)` builds the reason a code names. From `/orchestration`, `PolicyFailure` reasons are `Refusal`, `Missing` and `SequenceRefusal`.
- `isReactorFailure` recognizes any of the four failure classes, and `ReactorError.is`, `CommandFailure.is`, `AcquisitionFailure.is` and `PolicyFailure.is` each recognize their own class. `ReactorFailure` names their union.
- Every failure class has `isRetryable` and `retryAfter`, following Effect's `AiError`. `isRetryable` is true for the not-submitted `Overflow` of a pending-request bound, a connection lost before dispatch (`Disconnected`, `ChannelClosed`), an `Http` failure with no response or a 408, 429 or 503 or a `Retry-After`, and the `QueueFull` and `SessionRecovering` refusals. It is never true when `context.outcome` is `"unknown"`. `retryAfter` is the `Http` reason's `Duration`.
- `/orchestration` exports `EngineError = CommandFailure | PolicyFailure`, the failure of every engine command. Both carry `context.outcome`, so a classifier reads it without narrowing.
- Every type a public signature names can now be imported by name from the entry point that exposes it: `Observe`, `Observation`, `ReadyDescriptor`, `Ownership`, `Attribution`, `EventPayload` and `Correlation` from `reactor-effect-client`; `ClipOperation`, `ClipFact`, `ClipPhase` and `OperationFacts` from `/h3`; and `EngineObservation`, `ObserveEngine`, `RoutedRequest` and `EnqueueHooks` from `/orchestration`.
- `reactor-effect-native`: `NativeOptions.shutdownTimeout`, a `Duration.Input` that defaults to 10 seconds, bounds how long closing a connection waits for the native owner join. A value that is not a positive duration fails with `InvalidInput` when the layer is built; `"Infinity"` restores the unbounded wait.
- `reactor-effect-native`: `Native.Isolated.layer(options)`, an opt-in native host that runs each connection generation's native peer in a child process of its own, driven over Effect RPC, so a native crash or a wedged owner join ends that child's connection instead of the application. Building the layer preflights with a probe child; each peer forks its child when the factory makes it, and a dead child is never respawned: its dispatched calls fail with outcome `unknown` and later calls as `not-submitted`. Closing asks the child to join and exit within `shutdownTimeout` and otherwise kills it and reports `Shutdown`, then goes on to remote termination. Credentials, allocation, correlation and termination stay in the parent. It requires a Node.js parent (under Bun the layer fails with `UnsupportedCapability`) and costs a child start per generation and a copy of every frame. `@effect/platform-node` becomes a peer dependency of `reactor-effect-native`, as the install instructions already listed it; the package loads it only when the isolated layer is built. Frames keep their native admission `sequence` across the process boundary, so a frame the child evicts is a gap, as a frame the native queue drops is. The in-process `Native.layer` stays the default.

- The root exports the Schemas of the session descriptor and its parts, `SessionDescriptor`, `Capabilities`, `Track` and `Mapping`, and derives the `Descriptor`, `Capabilities`, `Track` and `Mapping` types from them. A field the provider sends as `null` or omits decodes as absent; `Descriptor.raw` still keeps what it sent.

### Changed

- **Breaking** for implementations of `EngineShape` or orchestration `Source`: both must provide `observe`. An orchestration now subscribes to each source's events when it registers the source, before anything else runs, instead of when its reader first runs, so no source event emitted in between is lost to the handoff's frame accounting.
- **Breaking:** every `VideoFrame` declares its pixel layout in `format: VideoFormat` (`"BGRA"` or `"RGBA"`); the native host produces `"BGRA"`, and a `RawMedia` implementation (or a simulation renderer) must set it. `MediaPressure` gains `readerOverflows`, the readers of a generation's tracks that fell behind their bound and failed with `Overflow`, so one snapshot covers every loss point; `RawMedia` implementations must report it.
- **Breaking** for `RawMedia` implementations and simulation renderers: `VideoFrame.data` and `metadata` are `Uint8Array<ArrayBuffer>` and `AudioFrame.samples` is `Int16Array<ArrayBuffer>`, so a frame's bytes can be transferred and never sit in a `SharedArrayBuffer`; the browser host's samples already were. Readers are unaffected.
- **Breaking:** an orchestration's `media.video` and `media.audio` admit one reader at a time: a second concurrent reader fails with `AlreadyReading` instead of silently splitting frames with the first. A reader that ends releases the output, and a later reader resumes from what is retained.
- An orchestration's `media.pressure` reports the loss of its logical output: `droppedVideo`, `droppedAudio` and `readerOverflows` now accumulate across source replacements, counting each source only while it fed the output, instead of restarting from the new source's counters. Mandatory consumption and the terminal `Overflow` of an undrained output are documented.
- **Breaking:** downloading a prepared recording is part of the portable client: `Coordinator.Client.downloadClip(clip, options)`, with `Coordinator.parsePlaylist` and the `Segment`, `DownloadOptions` and `DownloadedClip` types. `Browser.Recording.downloadClip` now takes the public `Coordinator.Client` from `Coordinator.make()` instead of the `/host` `CoordinatorClient`, so no application API needs `/host`. **Breaking (`/host` only):** `/host` no longer exports `CoordinatorClient` or `retryAfterMs`.
- **Breaking:** `orchestration.fromH3(session, provider, { media, ...policy })` is replaced by `orchestration.fromH3Session(session, { provider?, ...policy })`. The new constructor builds the session's H3 provider view and its decoded media itself, so a source can no longer pair one session's commands with another session's media, and returns them as an `H3Source` whose `provider` field exposes the provider's own operations. It needs a connected session on a host with decoded media, and otherwise fails with the session's own error (`UnsupportedCapability` on a host without decoded media) before any provider observation or policy command. `H3SourceOptions` is replaced by `SessionSourceOptions`.
- **Breaking:** a host is selected and validated when its layer is built. `Native.layer(options)` and `Browser.layer` are `Layer<PeerFactory, ReactorError>`: building the native layer loads Koffi and the library and verifies the staged artifact once, and building the browser layer detects WebRTC, so an unsupported host or an invalid native option fails there, before any `Client` exists to allocate a remote session. `Native.make` and `Browser.make` are removed, because `Effect.provide` would release the host layer when the factory effect ended; compose `Reactor.layer(configuration).pipe(Layer.provide(Native.layer(options)))` instead. `PeerFactoryShape.check` is optional and stateless: `make` no longer depends on it having run, and the session factory still runs it, when present, before every remote allocation.
- **Breaking:** `ReactorError`, `CommandFailure`, `AcquisitionFailure` and the orchestration `PolicyFailure` are independent `Schema.TaggedError` classes built from their fields, each with its own `_tag`, instead of `.extend` subclasses that shared `_tag: "ReactorError"`. `catchTag("PolicyFailure")` now compiles and `catchTag("ReactorError")` no longer catches the other three, none of which is an `instanceof ReactorError`; use `isReactorFailure` or a class's `is`. The positional `new ReactorError(code, message, context)` constructor is gone. `CommandFailure.from(error, context)`, `AcquisitionFailure.from(error, cleanup)` and `PolicyFailure.refuse(code, message, operation?, cause?)` build the derived forms, and `PolicyFailure.missing(purpose)` and `PolicyFailure.sequence(id, code)` the other refusals ([3f48e19]).
- **Breaking:** a failure's category moves from a flat `code` to its tagged `reason`, and there is no `code` alias: read `reason._tag`, whose values are the former codes and which `ErrorCode` still lists. `message` is the reason's message. `ErrorContext` keeps the operation, request, session, generation, outcome and the inspection-only `detail`; its `status`, `retryAfterMs`, `remoteCode` and `body` move into the `Http` and `Remote` reasons, and `retryAfterMs` becomes the `Duration` `retryAfter`. A 426 or 501 is still `VersionMismatch`, whose status and body are in `context.detail`. Diagnostic JSON now reads `{ _tag, message, reason, context }`.
- **Breaking:** `PolicyFailure.reason` is a closed union instead of an open string: a `Refusal` tagged `QueueFull`, `SessionRecovering`, `SessionClosed`, `SessionRetired`, `NotFound`, `OwnerConflict`, `Busy`, `InvalidRequest`, `PositionConflict`, `QueueChanged`, `RouteChanged`, `AnchorUnavailable`, `ContinuationUnavailable`, `AnnotationCapacity`, `SubmissionCapacity` or `IdentityExhausted`; `Missing`, whose `purpose` names the request field (the former `*_missing` strings); or `Sequence`, carrying the sequence's id and `SequenceError` code (the former `sequence_*` strings). Its `context` is `{ operation, outcome: "not-submitted" }`, with the outcome typed as that literal.
- **Breaking:** the root no longer exports `ProviderFailure`, and `ReactorError` loses the `nativeError` field, which nothing set; the typed reasons carry those fields. `ErrorContext` is exported as a type only.
- **Breaking:** signatures name what each operation raises. `EngineShape` and `Source` commands fail with `EngineError`, which replaces the `CommandError` and `EnqueueError` aliases. Orchestration and simulation `make`, `layerSim` and `Options.open` fail with `ReactorError | AcquisitionFailure`, and an `AcquisitionFailure` from `open` fails `make` unchanged. `fromH3` fails with `ReactorError | PolicyFailure | CommandFailure`, H3 `make`, `prepare` and `prepareFrom` with `ReactorError | CommandFailure`, and `Source.reconnect` with `ReactorError | CommandFailure`. The orchestration's terminal failure (`failure`, `SessionFailed`, `MediaState` and the orchestrated media streams) is the `ReactorFailure` it was raised as, so a replacement's `AcquisitionFailure` keeps its cleanup.
- **Breaking:** H3 prepare hooks and preparations may refuse with a `PolicyFailure`, which fails the submission unchanged instead of becoming a `CommandFailure` without its reason.
- **Breaking:** `Sequences.SequenceError` and `InvalidSequenceOptions` are `Schema.TaggedError` classes. `SequenceError.reason` is now `code`, listed by the exported `SequenceCode`, and `InvalidSequenceOptions.reason` is now `message`.
- **Breaking:** invalid `session.command` input (its name, data, uploads or deadline) fails as `InvalidInput`, not `Protocol`; it is still not submitted and sends nothing. A parser's rejection stays a typed failure while a bug in a parser, check or reducer stays a defect, instead of every throw becoming a typed `Protocol`.
- **Breaking (`/host` only):** `errorOf(cause, code, operation?)` requires its code and serves platform exceptions only; `parse` and `parsed` run a parser that rejects with a `ReactorError`, and let anything else it throws stay a defect.
- **Breaking:** every time option is an Effect `Duration.Input` named by its role, and a bare number is milliseconds, as everywhere in Effect, so a seconds value needs its unit: `leadSeconds: 30` becomes `lead: "30 seconds"`, because `lead: 30` is 30 milliseconds. NaN, which `Duration` decodes as zero, a negative value and a value past the option's maximum fail with `InvalidInput`, not submitted. `"Infinity"` disables the heartbeat, replacing `heartbeatMs: 0`, and marks a source that never expires. Each removed key stays declared as `?: never` through 0.3.0, so a configuration that still sets one, held or spread, fails to compile; the declarations go in the next minor. Measurements, instants and media lengths stay numbers: `requestRecordingClip(seconds)`, `ClipRequest.durationSeconds`, `ageSeconds`. `/host` exports the shared normalizer, `duration(input, name, policy)`.

- **Breaking:** `Session.command(name, data, options?)` and `Session.upload(name, mimeType, bytes, options?)` take an options object in place of their trailing positional arguments: `{ uploads?, replyTimeout? }` and `{ uploadTimeout? }`. Each override shares its key with the session's default, which it replaces for that call. `replyTimeout` is the session's own reply deadline: after dispatch it fails with `Timeout`, outcome `unknown` and the command's `requestId`, and the slot stays held until a late reply or the generation retires. To stop waiting without that, fork the command and bound `Fiber.join` with `Effect.timeout`. `reactor-effect-browser`'s `play(track, element, { playTimeout? })` does the same for its deadline. The compiler rejects every old call: a fourth argument is an arity error, and a bare uploads map or a number has no property in common with the options.
- H3 bounds each reference upload by its own `uploadTimeout`, 60 seconds by default, instead of its 15-second command budget.
- Coordinator replies (a session descriptor, a create reply's session id, ICE servers, a connection registration, an SDP answer, an upload allocation and a key exchange) are decoded by Schema after the bounded JSON copy, and the H3 `state_update` and `queue_update` cross-field rules are Schema filters. A malformed reply fails `Protocol` as before, with a message the library writes (`invalid session descriptor`, `H3 queue_update payload is malformed`) in place of the per-field one, and keeps the `SchemaError` in `context.detail`, which names the failing path but no input value. `reactor-effect-native` decodes a prepared mapping with the client's `Mapping` schema, so it also rejects an empty track name.
- **Breaking (`/host` only):** `/host` no longer exports `isRecord`, which `Predicate.isObject` replaces, or `readFileBytes`, which no host used; `uploadFile` still reads a file for an upload. It adds the time normalizer `duration`.
- An orchestration's `onRenewal` runs on a reader the handle forks, in order, instead of inline under the handle's command permit, so a slow renewal observer no longer delays `enqueue`, `setAutoplay` or any other command. Its failures are logged and do not stop later events; close waits up to one second for it to finish what was announced.
- **Breaking:** the orchestration `log` option is removed. The orchestration logs through Effect's logger at debug level, annotated with `module: "reactor.orchestration"`, so the application's logger and level decide what is kept. `log` stays declared as `?: never` through 0.3.0.
- **Breaking:** every `VideoFrame` and `AudioFrame` carries `sequence`, its admission number on its track in its generation, from 0, taken before any bounded queue could drop it, so a gap between two frames a reader receives is the count the host dropped there. A `RawMedia` implementation, or a simulation renderer, must set it.
- **Breaking:** `reactor-effect-native` loads only an ABI 4 native library: its frame and PCM headers carry the admission sequence (48 and 24 bytes), and an ABI 3 library, including one built from an earlier `main`, is rejected at layer build.
- **Breaking:** `ErrorCode` gains `ClipEnded` and `Indeterminate`, so an exhaustive match over the reason tags must handle them.
- **Breaking:** zero-argument operations are `Effect` values rather than functions returning one: `Coordinator.Client.pricing`, and `Peer.stats` and `Peer.shutdown` in the host peer contract (`Peers.Peer`). A custom `Peer` exposes `stats`, and `shutdown` when it has one, as values ([6291dc5]).
- **Breaking:** `ClipRequest`'s `durationSeconds`, `seed` and `position`, and `Coordinator.Inspection`'s `observedAt` and `additional` values are `Schema.Finite`, so NaN and infinities neither decode nor construct ([6291dc5]).
- **Breaking:** `reactor-effect-native` loads only an ABI 3 native library and rejects an ABI 2 library, including the 0.2.0 one passed as `libraryPath`. Decoded media now reaches JavaScript through bounded native queues drained with nonblocking takes, off the libuv thread pool, and every peer in a process shares one libwebrtc factory ([90f3b05]).
- **Breaking:** `ErrorCode` gains `SdpRejected`, `IceFailed`, `TransportFailed` and `ChannelClosed`, so an exhaustive match over the reason tags must handle them. A data channel that closes now fails the connection as `ChannelClosed` rather than `Disconnected`, and a failed native connection reports `IceFailed` or `TransportFailed` from its statistics ([90f3b05]).
- **Breaking (`/host` only):** `CoordinatorClient.create` resolves with the allocated session id and the reply, and the new `describe` decodes the session descriptor from it. `/host` serves the first-party host packages, which pin the exact client version.
- The three `ReactorError` messages that repeated provider text now carry a message written by the library: a data or control command's `Remote` error reads `remote command error <code>`, and a failed clip request reads `clip failed`. The provider's text moves to the `Remote` reason's `body`, which diagnostic serialization excludes, so code that read it from `message` reads `reason.body`, and routes on `reason._tag` and `reason.remoteCode`. A disabled recorder is still reported as `RecorderDisabled`, recognized from the clip failure's text; it is the one documented exception to never classifying provider text, until the wire carries a code for it.
- Each failure's native `cause` is its reason, as for Effect's `AiError`, and a reason holds no raw cause: a response body, a wire message, native backend text or a JSON `SyntaxError` quoting its input stays in `context.detail`, a `body` field or a Redacted field, so neither `Cause.pretty` nor an `OtlpTracer` export renders it. libwebrtc's text, which can contain peer SDP, is Redacted, and an HTTP body or a native backend message is also left out of a reason serialized on its own.
- `reactor-effect-browser`: a `play()` timeout's message reads `media play deadline` instead of `media read/copy/play deadline`; its reason is still `Timeout`.
- `reactor-effect-native`: while a timed-out owner join is still retained, preflight (`PeerFactory.check`) and peer creation for that library fail with a `Native` error that was not submitted, before any allocation, instead of starting another owner on a libwebrtc factory that may be wedged. The library admits peers again once the join completes.
- `VideoFrame` and `AudioFrame` document that every subscriber to a track receives the same frame object and buffers, so readers treat them as read-only and copy before writing. This was already the behavior.
- `reactor-effect-native`: the Rust library no longer panics outside tests, where a panic in a libwebrtc callback would abort the host process, and checks every pointer's alignment and length bound before touching caller memory ([efd9e51]).
- `reactor-effect-native`: the embedded build identity names the Reactor libwebrtc prebuilt the library links (`webrtcPrebuilt`), derived from the pinned `reactor-webrtc` checkout as its build script derives it, or `null` when `REACTOR_WEBRTC_LIB_DIR` or `REACTOR_WEBRTC_PREBUILT_URL` overrides it. Staging refuses a library whose prebuilt is not the tag the NOTICE declares or not the WebRTC milestone and commit of the platform's shipped SBOM, and release tooling requires every platform to link the same prebuilt.

### Removed

- `reactor-effect-client` no longer ships `notices/owned-webrtc/`. Those notices covered a reference project's own WebRTC and VP8 implementation, which no package contains. `notices/owned-webrtc-LICENSE` stays, for the session, correlation and observation code carried from that project.

### Fixed

- `provider.observe` no longer delivers an event its `initial` snapshot already reflects. A scheduler yield between the subscription and the snapshot read let the reducer apply a queued event that then appeared in both; events at or below `revision` are now dropped, as `session.observe` drops them, except acceptances, which no snapshot holds, and diagnostics without a source.
- A create reply that names its session but fails validation later, for example with an unknown track kind or malformed capabilities, no longer orphans the paid session. The session is recorded as owned from its id, the acquisition fails with a `Protocol` `AcquisitionFailure` whose `context.sessionId` names it, and cleanup deletes the session and confirms its termination (`cleanup.allocation` is `"known"`).
- JSON validation of caller input (command data, `extraArgs`, orchestration clip requests, H3 command data and `/wire`'s `structFromObject`) enforces its documented bounds. Object keys count toward the 4 MiB text budget; array holes and index accessors are rejected, and an accessor never runs; an array's length is charged against the node budget before any slot is read, so a sparse array with 100 million slots fails in milliseconds instead of passing after seconds. Each violation is still a typed failure that was not submitted. An array's non-index own keys are ignored, as `JSON.stringify` ignores them.
- A renewal `open` that returns a source whose `lifetime` is no longer than the renewal `lead` fails with `InvalidInput` instead of preparing a replacement immediately after every open, bounded only by `maxSessions`.
- Closing a media stream waits at most one second for the host's `ReadableStream` cancel before releasing its lock, so a cancel that never settles no longer holds the finalizer that runs ahead of paid-session termination.
- Checking an H3 provider's retained-byte bound no longer walks everything the provider retains on each event: a running total counts each retained object once, from when its first holder takes it until its last drops it. The bound is unchanged in meaning and may trip slightly earlier, because an object held by two retained entries counts twice.
- A minted token whose returned grant is refused keeps why in the failure's inspection-only `context.detail`, as other rejected replies do.
- An H3 refusal (`command_error`) keeps the provider's reason in its `Remote` reason's `body` instead of dropping it.
- `reactor-effect-browser`: the deadlines for resuming and closing the `AudioContext` in `audioContext()` and for starting playback in `play()` run on Effect's `Clock` instead of a wall-clock `setTimeout`, so `TestClock` controls them. Under the live clock they behave as before.
- `reactor-effect-native`: a native owner join that never completes no longer blocks `Session.close` and leaves the paid session running. At the `shutdownTimeout` deadline the close stops waiting, `CloseReport.localErrors` records a `Shutdown` failure ("native owner join exceeded its deadline; handle retained") and `localClosed` is false, and cleanup still terminates the remote session. The join keeps the native handle and its Koffi callback, and destroys and unregisters them only when it completes.
- A caller's JWT that the platform rejects as an HTTP header value fails as `InvalidInput` without keeping the platform's message, which quotes the value.
- `Coordinator.modelRate` finds a model that Reactor's pricing lists by its bare name. Sessions and tokens name models by slug (`reactor/h3-reference-to-video-turbo-realtime`), while the live pricing document lists `h3-reference-to-video-turbo-realtime`, so pricing an H3 session failed as `Protocol`. An entry named by the slug itself still matches; a document that lists the model under both names is ambiguous and fails, as one listing it twice does. It also reads the document as Reactor's billing documentation describes it: a rate per minute (`amount_per_min`), returned divided by 60 as `creditsPerSecond`; settings without `currency_code`, since credits are sold per US dollar; and an absent catalog, which prices nothing. Only the requested model's entry must hold a known rate, so another model's entry in any shape no longer fails every lookup.
- An H3 command that needs current facts no longer fails with `InvalidState` when it follows another command. H3 replies before it broadcasts the state and queue a command changed, so the provider is synchronizing between the two; a command sent in that gap, such as `submit` right after `setAutoplay(true)`, was refused. Such a command now waits, within `replyTimeout`, for the provider to become ready, and every command that needs facts settles once the broadcasts its reply implies are observed, so `current` after `submit` holds the queued clip. `getState` and `getQueue` still return without waiting.
- `reactor-effect-native`: classifying a failed connection as `IceFailed`, `TransportFailed` or `Disconnected` runs in the events pump under a 2 second deadline on Effect's `Clock`, instead of an unowned wall-clock `setTimeout`, so `TestClock` controls it and closing the connection stops it. Its outcomes are unchanged.

## [0.2.0] - 2026-09-23

Qualification: on September 22, 2026, before the canonical API migration and the workspace split, the ABI 2 bridge passed its Rust tests (including the real libwebrtc loopback), clippy with warnings denied and its JavaScript native tests on macOS arm64, and again in Linux x64 userspace under Rosetta translation, with glibc 2.36 on Node 24.14.1 and Bun 1.4.2. That Linux run found that Clang 14 cannot compile the pinned WebRTC headers, so the build recipes select Clang 21. Chrome 153 exchanged binary messages and media with the native bridge, directly and through a loopback-only Coturn 4.18.0 relay. No hosted Reactor generation was run. The full records are in the README at [eb0db13].

### Added

- First publication of the three packages, built from commit [eb0db13] and published to npm with SLSA provenance by the release workflow.
- `reactor-effect-client`: the canonical `Client` and scoped `Session` (allocation or attachment, commands, connection generations and cleanup evidence in `CloseReport`), coordinator operations (pricing, token minting, inspection, termination), the H3 provider (`/h3`), orchestration and renewal (`/orchestration`), an offline simulation (`/simulation`), test utilities (`/testing`), the generated wire codec (`/wire`) and the `/host` surface for host packages. It runs on Node 22 or newer, Bun and browsers, with Effect `4.0.0-rc.115`.
- `reactor-effect-browser`: an `RTCPeerConnection` host with generation-scoped tracks, media conversion and recording.
- `reactor-effect-native`: a libwebrtc bridge in Rust, loaded through Koffi (native ABI 2), with decoded media, file upload and staged libraries for linux-x64 and darwin-arm64, on Node and Bun.
