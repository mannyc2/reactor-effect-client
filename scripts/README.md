# Verification

`bun run verify` runs the same checks CI uses: the generated wire codec, formatting, lint, the dependency-ordered package build, every workspace's typecheck, the examples' offline tests, portable runtime imports and tests, native staging and tests, real local browser/native WebRTC, and clean installed-package validation. A profile is a list of stages: a stage's commands run side by side, and the next stage starts once they have all passed. The portable checks' first stage generates, checks formatting and builds; its second runs the import guards, lint, typecheck, the examples and the portable tests. A command running beside others has its output collected and printed whole, under its label and time, when it ends; a stage of one command streams its output live. Any failure stops the rest of its stage and the profile, and returns its nonzero exit status.

The profiles are `portable`, `shared`, `runtime`, `native`, `package`, `release` and `full`. Print a profile without executing it with `bun run verify --profile full --list`. `portable` needs no native binary. It is `shared` and `runtime` together: `shared` is the part whose outcome can't depend on the host (generation, formatting, build, lint, typecheck and the examples), which CI runs once, and `runtime` builds and runs only the portable tests and import guards, which CI runs for each host in its OS/Node matrix, where the Vitest suites run on that Node as well as on Bun. `native` builds the packages, then builds and stages the host's addon before checking it and running the public session integration. `package` checks the already staged addons without rebuilding them. `release` combines the portable and package checks; its native matrix must have qualified the staged artifacts first. `full` runs all three parts.

`test:portable` runs Vitest in `packages/client`, `packages/browser` and `integration/hosted` (the hosted qualification's gates, ledger and rehearsals), each under Node and under Bun, and this directory's own tests under Bun, side by side: as many at once as half the cores, and at least two, since each run spreads its files over the cores itself. `test:native` runs Vitest in `packages/native` under Node and then Bun, one at a time, so the media load tests measure the bridge rather than contention, and `test:integration` runs Vitest under Node in `integration`. There is no test filename registry: a new test in its workspace joins the corresponding project automatically. Each subprocess has a 180-second aggregate limit. The verification wrapper adds no shorter timeout, and CI sets no shorter job timeout.

## Files

| Path                   | Purpose                                                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `verify.ts`            | Profile orchestration; also runs the Node and Bun portable import guards after `build`   |
| `test.ts`              | Runs one test project with credential-like environment variables removed                 |
| `subprocess.ts`        | Runs a check's child without credential-like variables, live or beside others            |
| `portable-import.mjs`  | Imports every portable entry of the built client and browser packages                    |
| `examples.ts`          | Runs the examples' offline tests on Node and Bun and checks their browser bundles        |
| `wire.ts`              | Generates the wire codecs, or with `--check` compares them with the committed code       |
| `pack.ts`              | Packs, validates and installs the public packages into isolated consumers                |
| `pack-effect-stack.ts` | Selects the frozen Effect stack and validates workspace and consumer resolutions         |
| `pack/`                | Consumer fixtures copied into those isolated installations                               |
| `vitest.config.ts`     | This directory's own tests (`*.test.ts`), run under Bun                                  |
| `tsconfig.json`        | Typechecks this directory (JavaScript included); `pack/` is checked inside the consumers |

## Pinned tools and generated code

The root manifest pins Bun 1.4.2 and, through its catalog, TypeScript, Vitest, the Effect packages and their types; Oxlint and Oxfmt are root development dependencies. The formatter configuration disables import and package-key sorting and keeps generated wire code, native source, notices and staged libraries outside JavaScript formatting. Native formatting is checked by `cargo fmt` with the pinned Rust 1.90.0 toolchain.

Each package builds from its `tsconfig.build.json`, which is also its host closure: the client and browser packages compile with DOM types and no Node types, the native package with Node types and no DOM. `packages/client/tsconfig.node.json` checks the client without DOM types. Each package's `tsconfig.json` adds its tests and test runner types; `scripts/tsconfig.json` also checks this directory's JavaScript with `checkJs`. Each example workspace typechecks its TypeScript sources, which import one another with `.ts` specifiers so Node's type stripping runs them as they are.

After build, `check:examples` (`examples.ts`) runs each example workspace's offline tests under Node and under Bun and builds each browser bundle, all side by side, failing if a bundle reaches Node or native code. Credential variables are removed and examples that need a paid session are never executed. The tests that encode video need `ffmpeg`; they skip without it, and `EXAMPLES_REQUIRE_FFMPEG=1`, which CI sets, turns its absence into a failure.

`bun run generate:wire` (`wire.ts`) runs `buf generate` with `protoc-gen-es`, both pinned exactly as client devDependencies, over the tracked Reactor protos; Google's Struct comes with buf. There is no network or host-protoc dependency. It writes the client's codec to `packages/client/src/internal/proto` and the integration's browser far side's to `integration/browser/proto`, without the `eslint-disable` line protoc-gen-es opens each file with: the code passes the lint as generated, and lint reports a directive that suppresses nothing. `bun run generate:check` generates into a scratch directory and fails on any difference from the committed code. Schema changes must be reviewed alongside their generated diff.

## Installed-package and host evidence

`pack.ts` creates a fresh directory under `.check/pack-*` and preserves earlier archives. It packs each public package with `bun pm pack`, so `workspace:` and `catalog:` protocols are rewritten to exact versions; an archive that still carries either fails. For every archive it validates the exact public export map, all relative/declaration import closure, declared external dependencies, byte identity with the workspace build, the presence of README, LICENSE, NOTICE and `notices/`, Effect peers at exactly the selected versions (every archive peers on Effect, and native also on the Node platform and the shared platform) and, for the host packages, the exact `reactor-effect-client` peer.

The portable and browser installations omit optional dependencies, the native addon packages among them, and use a resolver that rejects dependencies outside their isolated directories and any resolution into `reactor-effect-native`. Their type consumers compile without a workspace fallback; the Node declaration consumer has no DOM library. The browser consumer installs the client and browser archives, type-checks its import fixture with the DOM library and no Node types, bundles every browser-safe entry from those installed packages, and runs the bundle without the Node `Buffer` global. The workspace examples are emitted in the isolated installations with strict dependency declaration checking (the portable Rundown in every consumer, the page in the browser one, the Node programs in the native one), and the compiled Rundown runs on the installed `ReactorTest` under both Node and Bun. TypeScript resolution traces remain alongside the archives. Temporary consumer trees are released after their checks by default to keep peak disk usage bounded. `KEEP_PACK_TMP=1` retains the extractions and all of this run's consumers. `--portable` skips the native archives and consumer. Each staged platform addon is packed as its own package: it must carry only its addon, its `native-identity.json` and notices, built from the checked-out sources, and the binding must carry no addon or Rust source and pin every platform package exactly. The native consumer installs the host's platform package beside the binding and runs its preflight through the installed addon.

Release qualification selects exact Effect, Node platform and shared-platform versions from the frozen `bun.lock` JSONC tuples. Before building, it checks that the catalog and the shared-platform override name exactly those versions, since the archives' peers come from the catalog, and resolves the packages from their declaring client/browser/native owners, including Effect and shared-platform edges through the platform owners. Missing, stale, malformed or mixed installations fail with a frozen-install diagnostic; there is no registry selection or lock refresh. A range there fails, even one the selection satisfies: a later Effect rc needs its own qualification and release.

The fresh consumer comes first. It installs only the client archive, always with npm, from a manifest that names no Effect version and sets no override, as an application's `npm install reactor-effect-client` does, so npm takes Effect from the registry through the archive's published peer. Every client module must then import on Node under the resolution guard, and `npm ls --all` must pass. Its install log and `fresh-node-dependencies.json` stay beside the archives; it records nothing in `package-identity.json`.

The portable and browser consumers install the selected exact Effect version by name. The native consumer, which runs only where the addons are staged, as in CI, names no Effect package and sets no override: the installer takes Effect, `@effect/platform-node` and `@effect/platform-node-shared` from the archives' exact peers, as an application's install does. No consumer sets overrides; npm applies them only from the root manifest of the project it installs, so a published package cannot pass one on. The read-only `npm ls` diagnostic runs for either installer and retains each consumer's dependency tree (`native-dependencies.json` for native). Every reachable Effect/platform occurrence must equal the selection; duplicate paths with the same version are recorded, while mixed versions and invalid dependency diagnostics fail.

Only after all consumer checks succeed, `package-identity.json.qualificationStack` records the lock SHA-256, original requirements, exact selections, workspace owner edges, and each completed consumer's installer and observed instances. The existing `.effect` field is the catalog's exact Effect version, which the release tooling checks. This metadata travels with the identity already retained by CI and release preparation; the current release schema validates its original fields and preserves the original raw bytes, while pack validates the added record. `bun --bun node_modules/vitest/vitest.mjs run --root scripts` exercises JSONC, exact requirements and archive peers (a range, or a later aligned RC the requirements don't name, fails), real owner-relative resolution, stale/mixed trees and incomplete evidence without registry access.

`package-identity.json` is also the release input. On `main`, CI's package job passes it to `release-tools/ci.mjs stamp`, which re-hashes the archives it names, writes `qualification.json` binding them to the exact commit, tree, run and attempt, and uploads the archives with both files as the flat `npm-package` artifact. The manual release workflow adopts that artifact without repacking; the ts-release application under `release-tools/` (its own lockfile, checked by `bun run check:release`) accepts only the `full` profile and rejects an identity whose packages disagree on version, whose export maps or file inventories changed, whose non-platform packages carry a `.node` addon, or whose native platform identities differ. See [release-tools/README.md](../release-tools/README.md).

The default consumer installer remains npm. `PACK_INSTALLER=bun` selects the same assertions with Bun's hoisted clonefile/hardlink installation explicitly; there is no automatic fallback after an npm failure. A SHA-256-named hardlink prevents reuse of a stale fixed-filename Bun cache entry. Every installed file of every archive is byte-checked against that exact archive for either installer, and the selected installer is recorded in `package-identity.json`. No workspace links or outside resolutions are allowed. Install diagnostics are retained as `install-<consumer>.log`.

Bun does not write the local-tarball provenance metadata that npm uses to validate a tarball dependency, including `file:` specs. After archive byte verification, the Bun consumer's own manifest records only those archives by their exact verified package versions so `npm ls` can validate the dependency graph; npm does not validate the original tarball spec. No reinstall or registry resolution follows this normalization. Installed package files stay untouched. The original manifest, normalized manifest and explicit normalization record are retained as `install-<consumer>.{manifest,normalized-manifest,normalization}.json`, alongside archive hashes and installer logs. A registry-disabled fixture reproduces the incompatibility and checks that wrong requirements, archive-byte mismatches, and missing/invalid peers still fail. Nonzero diagnostics, invalid dependency nodes, and mismatched stack versions remain failures. The npm installer keeps its install flags and needs no normalization; like Bun, it installs the exact selected versions, named or through exact peers, and every consumer passes the `npm ls` and recursive tree checks.

Each platform archive's `native-identity.json` must name its platform and addon, and the addon must match both that identity's SHA-256 and the staged file; every identity must have been built from the checked-out native sources (`stage.mjs --source-hash`). The installed native preflight checks the installed platform package against the qualified identity byte for byte, refuses an absent addon before anything could be allocated, and negotiates an offer through the installed addon. `PACK_EXPECT_NATIVE_PLATFORMS` lists the platforms whose staged addons must be present.

`native:build` is the staging entry point. `native:test` checks that staged artifact and does not silently build a second copy. The `native` verification profile runs them in that order. The public integration uses real Chrome WebRTC with local provider and media fixtures. It exercises public Browser and Native owners, ACK versus model replies, generation attribution, owned decoded bytes and media leases, failure cleanup and joined shutdown. It contacts no live Reactor session. TURN relay qualification remains an explicit separate opt-in using the existing integration environment settings.
