reactor-effect is for live audio and video production with [Effect](https://effect.website).
Applications choose generation capabilities, compose their providers with Layers, and consume
media streams. Reactor supplies video and audio through H3, FastH3 and Vidu S2-Avatar;
`CartesiaSpeech` supplies streaming text to speech through the provider-neutral `SpeechModel`.

Effect 4.0's `effect/ai/Model` already carries provider identity, model identity and a Layer. The
speech adapter uses it directly. Effect's language-model service does not define speech or video
generation, so these media capabilities have their own contracts.

Generation, scheduling and presentation are separate. Speech arrives as ordered PCM blocks before
its final duration is known. `Playout` schedules finite clips and manages their queue, deadlines
and source renewal. An application owns editorial priority, playback, mixing and proof of
presented output. The initial speech adapter does not schedule an unfinished utterance in Playout.

Reactor's allocated sessions retain their own lifecycle: expiring tokens, reconnection, ownership,
maximum length and termination evidence. An HTTP speech request does not acquire those semantics.
The [speech example](/reactor-effect-client/examples/#streaming-speech)
shows the independent path. Hosted Cartesia quality and latency have not been qualified.

## Three packages

| Package                  | What it gives you                                                                                                                                                                           | Runs in                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `reactor-effect-client`  | Streaming speech and its Cartesia adapter, Reactor sessions and providers, `Playout`, and `ReactorTest`. Portable: it loads no native code.                                                         | Node, Bun and browsers |
| `reactor-effect-browser` | The session's transport on the browser's own `RTCPeerConnection`, and playback of its tracks in DOM media elements.                                                                         | Browsers               |
| `reactor-effect-native`  | The session's transport on Reactor's `reactor-webrtc` crate (libwebrtc) through Node-API: decoded frames and PCM in your process, with an optional child process per connection under Node. | Node and Bun           |

The client owns every contract. A host package only carries the connection, so the same application
runs in a browser, on a server, or on `ReactorTest` with no transport at all.

## What it adds

<CardGrid>
  <Card title="A playout for continuous air" icon="rocket">
    `Playout` is a keyed schedule of clips in priority lanes, with filler that holds a runway,
    deadlines, cues and edits. It renews sessions before their cap and switches between them at a
    clip boundary, and reports what actually aired.
  </Card>
  <Card title="Decoded media without a browser" icon="laptop">
    Reactor's JavaScript SDK targets a browser context. On a server, `reactor-effect-native`
    complements it: Node and Bun receive the session's decoded frames and PCM directly, with no
    browser in between.
  </Card>
  <Card title="Reactor, offline" icon="setting">
    `ReactorTest` speaks the real wire protocol in memory, with H3's timing measured on paid runs
    and faults you can inject. With `TestClock`, an hour of programme runs in seconds and costs
    nothing.
  </Card>
  <Card title="Failures that say what reached Reactor" icon="approve-check">
    Every failed command carries its dispatch evidence: never sent, answered, or unknown. The SDK
    never sends an unknown command again, so a lost reply cannot play a clip twice.
  </Card>
</CardGrid>

## How it relates to Reactor's SDKs

Reactor publishes official SDKs for JavaScript, Python, C++, Swift and Java, and generated packages
per model. Use them when you want Reactor's own client in a browser, a game engine or a native app.

reactor-effect is independent and complementary. It is for TypeScript applications that are
written with Effect, or that need what Effect's structure gives a long-running media service:
resources tied to scopes, errors in the type, streams with back-pressure, and a clock you can
control in tests. It speaks Reactor's public coordinator API and wire protocol, and the requests
that create and connect a session carry its own `sdk_type`, so Reactor can tell its sessions apart.

<Aside>
  The Reactor adapters support **H3 Reference Turbo Realtime**, **FastH3** and **Vidu S2-Avatar**. Reactor's
  other models share the same session and wire protocol; each needs a provider module of its own,
  like `H3` or `ViduS2Avatar`.
</Aside>

## How it is qualified

- **Every change** runs the client, browser and hosted-rehearsal suites on Node and on Bun, real
  Chrome against the native host, and the examples. None of it allocates a paid session.
- **Hosted Reactor** is exercised by paid checks the maintainer runs with a budget: 26 runs from
  2026-09-24 to 2026-10-02, on the 0.3.0-rc.0 to 0.9.2 libraries. Each run records its evidence:
  frames, seams, timings, and every session confirmed ended. On 0.9.0 only the `showreel` check has
  run; 0.9.0's other checks, its published client packages, the browser package and the in-process
  native host under Node have not run there yet.
  [Hosted evidence](/reactor-effect-client/reference/hosted-evidence/) lists every run.
