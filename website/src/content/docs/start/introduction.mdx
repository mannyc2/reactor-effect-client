[Reactor](https://reactor.inc) serves real-time video models over WebRTC: you open a session, send
the model commands, and receive its video and audio as they are generated. reactor-effect is an
[Effect](https://effect.website) SDK for building applications on it, from a page that plays one
clip to a channel that stays on air for days.

It is built for the parts of a Reactor application that outlive a single request. A session bills
by the second until it ends, its token expires, its connection drops, its owner process crashes,
and the session itself has a maximum length. reactor-effect makes each of those an explicit, typed,
tested part of the API, so an application keeps its picture on air and never leaves a session
billing by accident.

## Three packages

| Package                  | What it gives you                                                                                                                             | Runs in                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `reactor-effect-client`  | Sessions and tokens, the H3 provider, `Playout`, and `ReactorTest`, Reactor simulated in memory. Portable: it loads no native code.           | Node, Bun and browsers |
| `reactor-effect-browser` | The session's transport on the browser's own `RTCPeerConnection`, and playback of its tracks in DOM media elements.                           | Browsers               |
| `reactor-effect-native`  | The session's transport on libwebrtc through Node-API: decoded frames and PCM in your process, with an optional child process per connection. | Node and Bun           |

The client owns every contract. A host package only carries the connection, so the same application
runs in a browser, on a server, or on `ReactorTest` with no transport at all.

## What it adds

<CardGrid>
  <Card title="A playout for continuous air" icon="rocket">
    `Playout` is a keyed schedule of clips in priority lanes, with filler that holds a runway,
    deadlines, cues and edits. It renews sessions before their cap and switches between them at a
    clip boundary, and reports what actually aired.
  </Card>
  <Card title="Decoded media without a browser" icon="laptop">
    Reactor's JavaScript SDK runs in a browser context, and its own TypeScript livestream starter
    launches headless Chromium to reach the media. `reactor-effect-native` hands Node and Bun the
    frames directly.
  </Card>
  <Card title="Reactor, offline" icon="setting">
    `ReactorTest` speaks the real wire protocol in memory, with H3's timing measured on paid runs
    and faults you can inject. With `TestClock`, an hour of programme runs in seconds and costs
    nothing.
  </Card>
  <Card title="Failures that say what reached Reactor" icon="approve-check">
    Every failed command carries its dispatch evidence: never sent, answered, or unknown. The SDK
    never sends an unknown command again, so a lost reply cannot play a clip twice.
  </Card>
</CardGrid>

## How it relates to Reactor's SDKs

Reactor publishes official SDKs for JavaScript, Python, C++, Swift and Java, and generated packages
per model. Use them when you want Reactor's own client in a browser, a game engine or a native app.

reactor-effect is independent and complementary. It is for TypeScript applications that are
written with Effect, or that need what Effect's structure gives a long-running media service:
resources tied to scopes, errors in the type, streams with back-pressure, and a clock you can
control in tests. It speaks Reactor's public coordinator API and wire protocol, and the requests
that create and connect a session carry its own `sdk_type`, so Reactor can tell its sessions apart.

<Aside>
  reactor-effect supports **H3 Reference Turbo Realtime** today. Reactor's other models share the
  same session and wire protocol; each needs a provider module of its own, like `H3`.
</Aside>

## How it is qualified

- **Every change** runs the client, browser and hosted-rehearsal suites on Node and on Bun, real
  Chrome against the native host, and the examples, all against `ReactorTest`. CI never allocates a
  paid session.
- **Hosted Reactor** is exercised by paid checks the maintainer runs with a budget. Each run records
  its evidence: frames, seams, timings, and every session confirmed ended.
  [Hosted evidence](/reactor-effect-client/reference/hosted-evidence/) lists them all.
