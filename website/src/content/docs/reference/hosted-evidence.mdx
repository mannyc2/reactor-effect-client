Every claim on this site about hosted Reactor rests on a paid run listed here. Each run is one
check of the [hosted harness](https://github.com/mannyc2/reactor-effect-client/tree/main/integration/hosted),
an Effect program over the public API, run by the maintainer against hosted H3 Reference Turbo
Realtime (`reactor/h3-reference-to-video-turbo-realtime`). Its evidence file and summary are
committed under `integration/hosted/evidence/`, with the session ids, so Reactor can find its side
of each run.

<Aside type="note" title="Hosted and rehearsed are kept apart">
  CI runs every check as a rehearsal on `ReactorTest`, the simulated Reactor, and never allocates a
  paid session. A rehearsal shows the program is right about the contract it simulates; it is not
  evidence of what hosted Reactor does, and nothing on this page comes from one.
</Aside>

The harness refuses to run without `--i-authorize-paid-sessions` and a budget. Each run reserves
its worst case in a ledger before any token exists, and a ledger's total is capped at $5.

## Billing records

- The Reactor dashboard listed each session's duration to the second, matching the time from
  allocation to the `DELETE` within a second (0.8.0-api), and listed a 10-second session at 10 s,
  so Reactor meters by the second (0.8.0-probe).
- Whether the meter starts at creation or at `ready` stayed open: `ready` came 0.19–0.38 s after
  allocation, under the dashboard's one-second resolution.
- The balance readings fit neither the published rate nor whole minutes. 0.3.0-rc.0's third run
  moved the balance by $0.03–0.05, against $0.11 at the published rate; 0.8.0-dev's sessions had not
  moved it hours later; and the $1.09 between the readings around 0.8.0-probe fits neither.

## What the runs found about the platform

These are behaviours of hosted Reactor and H3 the runs recorded, worth knowing whatever client you
use:

- H3 broadcasts the `queue_update` listing a new clip before the enqueue's correlated
  `clip_queued` reply (0.3.0-rc.0).
- An attached connection receives no media until it resumes its tracks, as Reactor's sessions page
  says (0.3.0-rc.0).
- The deployment reports version `v0.0.0`, where the documented schema is 0.5.5 (0.3.0-rc.0,
  0.3.1).
- A position-zero enqueue went ahead of the build in flight, where the schema says the running
  build is unaffected (0.6.0, 0.7.0). A queue read sent 1 ms behind an enqueue listed the new clip:
  commands applied in the order sent (0.7.0).
- `stop` names no clip and lands after its reply; under autoplay it skips to the next clip, so a
  second `stop` cuts that one (0.7.0).
- H3 flushes to black at each clip's end by default (`flush_on_clip_end`), one dark frame per seam
  (0.6.0, 0.7.0); holding the last frame removes it.
- A session whose last connection has gone reads `INACTIVE` and is still live (0.8.0-dev); it read
  `ACTIVE` for about 2.1 s after its last connection closed (0.8.0-api).
- Content moderation's `terminate` verdict came 0.40–1.01 s after the flagged enqueue, which had
  been answered normally, and named no category, input, command or request (0.8.0-dev, 0.8.0-api).
- A 16,171-character prompt was accepted, then failed by `clip_failed` 2.39 s later: H3's text
  budget is enforced at build (0.8.0-api).
- A clip recording came back `ClipReady` in 2.6 s, but its download timed out at 15.1 s
  (0.8.0-api).
- A session allocated and never connected read `ACTIVE` throughout and was ended by Reactor at its
  60-second cap, 60.09 s after allocation; a second create on a spent single-session token was
  refused with 403 (0.8.0-probe).

## Not yet run on hosted Reactor

- **0.9.0's published bytes.** No paid run has exercised 0.9.0: `Playout.place` and `follows`, the
  `CoordinatorClient` rename and 0.9.0's fixes have run only on `ReactorTest`. The newest runs used
  a checkout matching the 0.8.0 release.
- **The `turn` check**, the vertical from a network that blocks outbound UDP so a relay must carry
  the media. Every paid run went over a direct path.
- **`reactor-effect-browser`.** No paid run has used the browser host.
- **macOS arm64.** Every paid run was on Linux x64. The in-process native host ran under Bun, and
  the isolated host under Node.
- **Long sessions.** The longest paid run lasted under two minutes; no multi-hour renewal soak has
  run.
- **Restreaming and native publication.** No run has sent native media on to a browser, to RTMP or
  to LiveKit.
